# 第18篇：四种编排怎么选｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 18 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

十七篇过去，每篇都在解决一个具体问题。最后一篇不教新 API，只回答一个绕不开的问题：手上这个任务，到底该用哪一层来编？

## 一、四层，先摞清楚

官方把这件事拆成三个角色，外加一个横切层：

- **LangGraph 是运行时**：负责持久执行、流式输出、人审中断、状态持久化，给你每一步的控制权；
- **LangChain 是框架**：模型、工具、agent loop 的抽象，`create_agent` 是最小的一套循环，它本身跑在 LangGraph 上；
- **Deep Agents 是 harness**：预装了文件系统、子 Agent、技能、记忆、任务清单，底层还是前两层；
- **LangSmith 是观测层**：跨框架，负责 trace、评估、部署。

关系是单向的：上层依赖下层，但用上层**不需要**手写下层代码。这就是选型的全部空间。

## 二、判断顺序：从需求问，不从工具问

很多人反过来问"哪个框架更强"，答案永远是"看你要什么"。按下面四个问题依次问，第一个"是"就是你的层：

1. **有 agent loop 吗？** 只是模型调用、检索、固定提示链，没有"调工具—看结果—再决定"的循环，那就别上框架，直接写链；
2. **循环是标准的吗？** 一个模型、一组固定工具、跑完就答，`create_agent` 足够，中间要护栏、日志、结构化输出，加 middleware 就行；
3. **要规划、文件、跨会话记忆、子 Agent、按需加载的技能吗？** 只要占了两项以上，Deep Agents 的预装件比你自己拼省事得多；
4. **图的形状本身不对吗？** 固定步骤和智能步骤要混排、要分支、要精确的中断点、要回放重跑，这时候只有 LangGraph 能表达。

注意第 1 问必须最先问。跳过它，后面三层都会为"根本不需要循环"的任务多付成本。

```python
# 没有循环：一次调用就结束，不必包 agent
reply = model.invoke("把这封邮件分类：客户说发票开错了金额")
```


## 三、LangChain：最小循环够用的地方

百川归海，大多数 agent 其实就是"一个模型 + 一组工具 + 一句人设"。这类活用 `create_agent`，代码量最小：

```python
from langchain.agents import create_agent

agent = create_agent(
    model="openai:gpt-5",
    tools=[search_docs, fetch_page],
    system_prompt="先检索，再回答；每个结论后面带来源链接。",
    middleware=[trim_messages],        # 上下文太长时裁一裁
)
reply = agent.invoke({"messages": [{"role": "user", "content": "查一下 LangGraph 1.2 的变更"}]})
```

边界也很清楚：它表达不了条件分支，跑不了多个 Agent 协作，重启后不能从断点续跑，也不能真的去读写文件。**这些不是缺陷，是这一层刻意不做的部分。**

## 四、LangGraph：什么时候必须画图

一句话判断：**当"下一步做什么"不能交给模型决定时，就该画图。**

具体是四种情形：固定步骤和智能步骤混在一条流水线里（先抽取、再打分、再分流）；有明确的分支与并行；中断点必须精确落在某一步之前；出问题要能回到某个检查点重跑。

```python
from langgraph.graph import StateGraph, START, END

def route(state):
    return "manual" if state["score"] < 60 else "auto"

builder = StateGraph(Application)
builder.add_node("extract", extract_node)
builder.add_node("score", score_node)
builder.add_node("auto", auto_approve)
builder.add_node("manual", escalate_to_human)
builder.add_edge(START, "extract")
builder.add_edge("extract", "score")
builder.add_conditional_edges("score", route, {"auto": "auto", "manual": "manual"})
graph = builder.compile(checkpointer=checkpointer)
```

代价要认：流程一改，节点和边都得跟着改；状态 schema 要自己设计；每一步的输入输出都要能讲清楚。画图换来的是"可解释"，付出去的是"灵活"。

## 五、Deep Agents：预装的那一整套

长任务最难的不是推理，是上下文管理。Deep Agents 把这件事做成了默认件：虚拟文件系统（可换内存、本地盘、store 或沙箱后端）、子 Agent（默认隔离上下文，`mode="fork"` 才继承父历史）、技能、跨会话记忆，以及用 `interrupt_on` 指定哪些工具要先批。

```python
from deepagents import create_deep_agent
from langchain.agents.middleware import TodoListMiddleware

agent = create_deep_agent(
    model="openai:gpt-5",
    tools=[search_docs],
    system_prompt="你是研究助手：先列计划，再把长材料落到文件里，最后成稿。",
    middleware=[TodoListMiddleware()],   # 0.7 起任务清单是 opt-in
    interrupt_on={"write_file": True},   # 落盘前先等人批
)
```

有个版本细节值得单独记：**0.7 起，任务规划从默认变成 opt-in**，想要 `write_todos` 必须自己传 `TodoListMiddleware`。老代码升级后"怎么不列计划了"，八成就卡在这。

部署也有两档：想省基础设施就用 Managed Deep Agents，harness、Agent Server、沙箱、定时都由平台跑；要自己控运行时，就用 SDK 挂在自建的 Agent Server 上。两档用的是同一套 harness，迁移时改的是部署方式，不是代码结构。

## 六、混合：harness 里塞自研子图

真实项目很少只用一层。最常见的落法是：标准循环交给 harness，形状特殊的部分做成子图塞回去——任何 LangGraph 的编译产物都能作为子 Agent 挂进 Deep Agent。

```python
graph = build_pricing_graph()      # 普通 LangGraph 编译产物，内部有分支和中断

agent = create_deep_agent(
    model="openai:gpt-5",
    tools=[search_docs],
    subagents=[{"name": "pricing_flow",
                "description": "按固定流水线跑三家竞品的定价对比",
                "graph": graph}],
)
```

这样主 Agent 负责"要不要跑、跑完怎么用"，子图负责"每一步按规矩走"。两边的边界只有一个：子图的输入输出必须能写成一段清晰的描述。

## 七、代价表

加一层不是免费的。把多付的东西先摆出来：

| 选哪层 | 你多付什么 | 什么时候值 |
|---|---|---|
| LangChain | 几乎没有额外成本 | 单用途、固定工具、跑完就答 |
| LangGraph | 自己管状态、边、检查点 | 流程可画、要分支、要回放 |
| Deep Agents | 更多 token、更长的调试链路、跟版本 | 长任务、多步、要文件和子 Agent |
| 混合 | 两套概念、边界要对齐 | 大多数真实项目 |
| LangSmith | 接入与数据出网 | 只要上线就值得 |

Deep Agents 多付 token 是结构性的：预装的工具定义、系统提示、子 Agent 的回报都要占窗口。省下来的不是钱，是你自己拼这套东西的时间。

## 八、四个反例

1. **三步任务上 harness**：明明一句提示加两个工具就够，结果多出文件系统、子 Agent、任务清单，出了问题不知道是哪一层加的戏。
2. **单循环硬画图**：为了"显得工程化"，把一个聊天 agent 拆成五个节点，改一句人设要动三条边。
3. **把 harness 当"更聪明的 create_agent"**：不看它默认塞了什么工具和提示，直接上生产，最后发现模型在调你根本没打算给它的能力。
4. **不上观测就选型**：没有 trace 的横向对比都是猜。同一批任务跑三遍，看每一步耗时、token、失败点，才有得选。

这四条反例的共同点，是把"层"当成了"能力等级"。层与层之间不是强弱的排序，是职责的分工：越往上，预装件越多、你要想的事越少；越往下，控制越细、你要写的代码越多。

## 九、一句话收尾

选型不是选最强的，是选**"能解释清楚每一步为什么发生"的那一层**——解释得清，出问题就能修；解释不清，再高级也只是黑箱换了个壳。
