# 第04篇：工具怎么被模型看见｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 04 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

前三篇看的是循环、消息和钩子，都在 Agent 内部。这一篇往外看一步：循环里唯一能碰到真实世界的东西——工具。

## 一、模型只拿到一张说明书

一个工具由两半组成。一半是发给模型的说明书：名字、一句话描述、参数结构。另一半留在你的进程里：函数体、密钥、数据库连接、权限校验。模型从头到尾看不到后者。

它做的事只有一件：按说明书发出一个带参数的调用请求。你这边执行完，把结果包成一条消息塞回对话，它再决定下一步。所以"工具调用"从来不是模型在调用你的代码，而是模型在填一张表单。

`@tool` 把这张表单自动生成出来：类型标注变成参数 schema，docstring 变成 description。类型标注是必需的，没有它就拼不出 schema。

```python
from typing import Literal
from langchain.tools import tool

@tool
def search_orders(
    user_id: str,
    status: Literal["paid", "refund"] = "paid",
    limit: int = 5,
) -> str:
    """查询某个用户的订单列表，可按支付状态过滤。"""
    ...
```

这时候模型看到的参数只有三个。如果你在函数签名里加一个 `runtime: ToolRuntime`，它会被从 schema 里摘掉——模型不知道有这个参数，也永远传不进来。这是整套机制里最关键的一条：注入的东西不进说明书。

## 二、description 决定它被不被调用

模型选工具不靠读代码，靠读名字和描述。名字用 snake_case，别用空格和特殊字符，部分厂商会直接拒掉。描述写"什么时候该用它"，而不是"这个函数内部做了什么"。

反例很常见：两个工具描述都写"查询数据"，模型只能猜。正例是把边界写进描述——一个叫"按订单号查单条"，一个叫"按手机号查最近五条"，模型一眼就知道该挑哪个。

工具太多时，描述还要承担分流。十几个工具全用"处理用户请求"这种万能描述，模型的错误率会明显上升。经验值：单次暴露给模型的工具控制在 10 个上下，超了就分组，或者按对话阶段分批给。

另外两个保留参数名要避开：`config` 和 `runtime`。工具参数叫这两个名字，运行时会直接报错。

## 三、参数结构有三种写法

简单工具用函数签名就够。复杂输入上 Pydantic 或 JSON Schema，把枚举、范围、默认值写清楚，等于帮模型缩小搜索空间。

```python
from pydantic import BaseModel, Field

class WeatherInput(BaseModel):
    """天气查询的输入。"""
    location: str = Field(description="城市名或经纬度")
    units: Literal["celsius", "fahrenheit"] = Field(default="celsius")
    include_forecast: bool = Field(default=False, description="是否要 5 天预报")

@tool(args_schema=WeatherInput)
def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
    """查当前天气，可选未来 5 天预报。"""
    ...
```

一条原则：能推断的不要问模型。当前用户 id、租户、请求时间、会话 id，这些从 runtime 取，不要做成参数让模型去编——它一定会编出一个看起来很合理的值。

## 四、返回什么，决定下一轮怎么想

同一个工具，出口不同，模型拿到的东西完全不同。

返回字符串，它变成一条 `ToolMessage` 的文本，模型读文字做判断。返回字典或对象，序列化后同样进 `ToolMessage`，但模型能按字段读、按字段引用，适合结构化数据。

返回 content blocks，就是多模态工具结果：文字加图片、音频一起回来。前提是模型支持这种模态，不然它读不了。

返回 `Command`，工具就不只是给结果，还能改 state。这时必须同时带一条 `tool_call_id` 对得上的 `ToolMessage`，否则 `ToolNode` 会抛 `ValueError`——每条工具调用都必须有对应的回复，这条不变量不能破。

```python
from langchain.messages import ToolMessage
from langchain.tools import ToolRuntime, tool
from langgraph.types import Command

@tool
def set_language(language: str, runtime: ToolRuntime) -> Command:
    """设置本会话的回复语言。"""
    return Command(update={
        "preferred_language": language,
        "messages": [ToolMessage(
            content=f"语言已设为 {language}",
            tool_call_id=runtime.tool_call_id,
        )],
    })
```

还有一种是 `return_direct=True`：工具结果直接当最终答复，跳过下一轮模型调用。适合查订单状态这种"结果就是答案"的场景，缺点是模型不能再改写、总结、串联。并行调用时要注意，只有这一批里每个工具都是 `return_direct`，循环才会结束。

## 五、runtime：模型看不见的那一半

`ToolRuntime` 是后台通行证，模型只知道有三个参数，不知道工具内部还能摸到这些：

- `runtime.state`：当前消息列表和自定义字段
- `runtime.context`：本次调用的不可变配置，比如 user_id、租户
- `runtime.store`：跨会话长期记忆
- `runtime.stream_writer`：边执行边往外推流，做进度条用
- `runtime.execution_info`：thread、run、第几次重试
- `runtime.tool_call_id`：回填 `ToolMessage` 时对账用

```python
@tool
def my_orders(runtime: ToolRuntime[UserContext]) -> str:
    """查当前用户自己的订单。"""
    uid = runtime.context.user_id
    return query(uid, runtime.state.get("order_filter", {}))
```

把说明书和实现分开看，很多设计就顺了：schema 越简单越好，因为那是给模型看的；权限、身份、连接全放 runtime，因为那是给你自己用的。工具可以同时"参数很少"和"权限很严"。

## 六、工具太多，就按需给

工具数量是上下文成本。全塞进去，模型选择困难，token 也烧得快。两种做法，取决于工具是不是提前就知道。

提前知道，就全部预注册，用 `wrap_model_call` 按权限、开关、对话阶段过滤：

```python
from langchain.agents.middleware import wrap_model_call

@wrap_model_call
def only_public(request, handler):
    if not request.state.get("authenticated"):
        request = request.override(
            tools=[t for t in request.tools if t.name.startswith("public_")]
        )
    return handler(request)
```

运行时才发现——比如从 MCP 服务器拉回来、按用户数据临时生成——就要同时写两个钩子：`wrap_model_call` 把工具加进请求，`wrap_tool_call` 负责执行。少写后者，模型会调一个没人接的名字。

## 七、结构化输出，其实是造一个工具

`response_format` 有三种给法，对应两种策略。

`ProviderStrategy(Schema)`：schema 直接进厂商的原生 structured output，由服务端保证 JSON 形状，最严格，也最可靠。

`ToolStrategy(Schema)`：把 schema 伪装成一个工具，模型"调用"它来交答案。所有支持工具调用的模型都能用，代价是多一次工具往返。

直接给 `Schema`：LangChain 自动选——模型支持原生结构化输出就用 Provider，不支持退回 Tool。

Tool 策略还自带容错。`handle_errors=True` 是默认值：校验失败时，错误被包成一条 `ToolMessage` 回给模型，让它自己改。`tool_message_content` 可以把那条消息换成你想要的文案。`Union[A, B]` 还能让模型在多个形状里选一个。最终结果统一落在 state 的 `structured_response` 里。

所以"让模型输出 JSON"和"给模型一个工具"，在这套框架里几乎是同一件事。

## 八、报错也要让模型看见

工具抛异常，默认会打断整轮执行。更好的做法是把异常翻译成模型能读的消息，让它自己修参数重试：

```python
from collections.abc import Callable
from langchain.agents.middleware import wrap_tool_call
from langchain.messages import ToolMessage
from langchain.tools.tool_node import ToolCallRequest

@wrap_tool_call
def handle_tool_errors(
    request: ToolCallRequest,
    handler: Callable[[ToolCallRequest], ToolMessage],
) -> ToolMessage:
    try:
        return handler(request)
    except Exception as e:
        return ToolMessage(
            content=f"工具报错，请检查参数后重试：{e}",
            tool_call_id=request.tool_call["id"],
        )
```

注意这条消息必须带 `tool_call_id`，否则对话结构就断了——第 02 篇讲过的对账规则，在这里同样成立。

一句话收尾：工具的边界不在函数里，在说明书里。你写 description 和 schema 有多认真，直接决定模型会不会用错。
