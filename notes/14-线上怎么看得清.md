# 第14篇：线上怎么看得清｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 14 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

第 13 篇把失败处理配齐了，但"配得对不对"不能靠猜。这一篇讲上线之后怎么看：数据按什么结构存、一条 trace 里该盯哪几个位置、看到的问题怎么变成下次发版前的回归用例。

## 一、四层结构，先分清

LangSmith 把观测数据分成四层，名字很像，混起来就白看了：

| 概念 | 形状 | 装什么 | 什么时候看 |
|---|---|---|---|
| run | 单个节点（span） | 一次模型调用、一次工具调用 | 定位到具体一步 |
| trace | run 的树 | 一次请求涉及的全部 run | 一次操作为什么慢、为什么错 |
| thread | trace 序列 | 多轮会话的每一轮 | 用户聊到第几轮开始跑偏 |
| trajectory | 扁平消息列表 | 会话里交换的全部消息，按首次出现排序去重 | 只关心"说了什么"，不关心执行细节 |

一句话记：run 是砖，trace 是一栋楼，thread 是一排楼，trajectory 是把这排楼拆成一份对话记录。

有个硬限制要知道：**一条 trace 最多 25,000 个 run**，超了新的 run 会被拒收。正常 Agent 一轮也就几十个 run，但如果你在循环里疯狂扇出，这个数不是遥不可及。

## 二、先把身份打上

默认情况下所有 trace 混在一起，出问题根本筛不出来。三个东西必须在调用时传进去：

```python
config = {
    "configurable": {"thread_id": thread_id},
    "metadata": {"env": "prod", "agent_version": "v2.3", "tenant": tenant_id},
    "tags": ["prod", "checkout"],
}
graph.invoke(inputs, config)
```

- `thread_id`：按 metadata 传，多轮会话才会被串成一条 thread；
- `metadata`：版本号、租户、环境这类上下文，用来过滤和分组；
- `tags`：字符串标签，做粗筛和分组最方便。

另外 LangSmith 现在按 agent 分环境（Production / Staging / Development / Local），生产流量和测试流量天然分仓，不必再靠手写条件排除。

只想采一段样本、不想全量上报时，用 `tracing_context` 包一层：

```python
import langsmith as ls

with ls.tracing_context(enabled=True):
    graph.invoke(inputs, config)     # 这一段上行，其余按环境变量走
```

## 三、一条 trace 看四个位置

打开一条 trace，别从第一个 run 往下读，按这个顺序看效率最高：

1. **根 run 的总耗时**：先判断是"整体都慢"还是"某一步慢"；
2. **最慢的那个 run**：LangGraph 里每个节点是一个 run，子图是嵌套的 run，耗时会挂在具体节点上，不会含糊；
3. **失败位置和重试记录**：重试过的节点在树里会留下多次尝试，配合第 13 篇的 `NodeTimeoutError` 一起看，能区分"接口慢"还是"重试策略太激进"；
4. **token 与成本**：模型 run 上带用量，成本异常往往先出现在这里，而不是在报错里。

如果这条 trace 是用户投诉的那一条，记得回到第二节讲的 metadata：没有版本号，你没法确认它跑的是哪一版 prompt。

## 四、thread 和 trajectory 是另一个视角

trace 回答"这一次为什么错"，thread 回答"这个用户是怎么一步步被带偏的"。

按 thread 看，你能看到第 3 轮之后每轮都要多绕两个节点——这通常是上下文被污染，而不是单步逻辑有 bug。第 11 篇讲子图隔离，正是为了解决这类问题。

trajectory 更轻：它把整条 thread 拍平成"人说了什么、AI 回了什么、工具返回了什么"，去掉了嵌套和耗时。跟产品、运营对齐行为时用这个，比拉着一张巨大的 run 树讲要省力得多。

## 五、trace 会过期，证据要另存

这是最容易踩的坑：**trace 只在套餐的保留期内存在**，到期永久删除，只留少量元数据做统计。

也就是说，昨天那条让你拍桌子的失败 trace，下周可能就点不开了。要留证据，唯一的办法是把它变成 dataset 里的 example——**dataset 是永久保留的**，源 trace 删了也不影响。

所以看到值得留的失败，当场就收集，别等"回头再整理"。

## 六、回归集从十条开始

dataset 的结构很简单：一堆 example，每条有 `inputs`、可选的 `reference outputs`、可选的 `metadata`。reference outputs 不会传给你的应用，只在评估器里用。

建集子按这个顺序来：

1. **手工写 10–20 条**：覆盖常见场景加两三个边界，这是官方推荐的起点，也最快见效；
2. **从线上 trace 转**：真实失败比想象出来的用例更值钱；
3. **标注队列回收**：人工审过的 case 直接进集子；
4. **补量**：CSV / JSONL 导入，或从已有样例合成。

分集的判据是"测的是不是同一种行为"：同一种行为、同一批评估器，放同一个 dataset，实验才可比；输入形态变了（单轮变多轮）、评估器要换、用途不同（PR 小集 vs 发版大集），就另开一个。同一个集子里还能用 splits 拆子集。

建集子就是两行：

```python
client = ls.Client()
dataset = client.create_dataset("checkout_refund_v1")
client.create_examples(dataset_id=dataset.id, examples=[
    {"inputs": {"q": "退款多久到账"}, "outputs": {"must_contain": "3-5 个工作日"}},
    {"inputs": {"q": "能退到信用卡吗"}, "outputs": {"must_contain": "原路退回"}},
])
```

## 七、评估器与 experiment

评估器分四类，够用了：

- 人工审：最准，最贵；
- 代码规则：格式、字段、必须包含的关键词，跑得最快；
- LLM-as-judge：开放式回答只能靠它，但要写清评分标准；
- pairwise：两个版本二选一，比绝对打分稳。

代码规则类的评估器长这样，三个入参对应输入、应用输出、参考答案：

```python
def must_contain(inputs, outputs, reference_outputs):
    want = reference_outputs["must_contain"]
    return {"key": "must_contain", "score": want in outputs["text"]}
```

规则评估器要写成"能失败"的：永远返回 1 分的评估器，除了让报表好看，没有任何作用。

一次 experiment 就是"某个版本在一份 dataset 上的结果"，里面存着每条的输出、评估器分数和执行 trace。所以"这版比上版好"不是感觉，是两份 experiment 摆在一起比。

```python
results = client.evaluate(
    lambda x: graph.invoke({"messages": x["messages"]}),
    data=dataset.name,
    evaluators=[must_contain, judge_relevance],   # 代码规则 + LLM 判分
    experiment_prefix="v2.3",
)
```

想省成本，可以在配置里调重复次数、并发和缓存。

## 八、线上评估与闭环

离线跑完不等于线上没事。线上评估做的是另一件事：**在生产 trace 上自动跑无参考答案的评估器**——安全、格式、质量启发式、无参考的 LLM 判分，按采样率控制成本。

采样率别一上来就 100%：先按 1% 跑一周，看误报量，再往上调。评估器本身也要盯，判错的评估器比没有更糟。

闭环就一圈：在线评估发现的坏 case，加进 dataset；下次发版前，离线在这个集子上跑一遍，分数不许掉。分数掉了，就是这一版引入的回归。

最后提醒一句：别只看平均分。Agent 的问题几乎都在尾部——95 分位耗时、少数几条彻底跑飞的 trace。平均值会把它们抹平。

## 九、一句话收尾

观测不是"接个 SDK 就完事"，它有三条硬约束：**结构要对（run/trace/thread/trajectory 分清）、身份要打（thread_id + metadata + tags）、证据要存（trace 会过期，dataset 不会）**。

三条都做了，你才有资格谈"这次改动有没有变好"。否则每次发版都像掷骰子，只是掷得比较贵。
