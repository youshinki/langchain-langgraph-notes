# 第11篇：子图怎么隔上下文｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 11 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

第 10 篇讲流式，这一篇讲多 agent 的第一性问题：上下文怎么隔。所谓"专家 agent"，真正的价值不是换个提示词，而是让它在自己的上下文里干活，别把整段历史都背过来。LangGraph 把这件事拆成两件可配的事——状态怎么接、检查点怎么存。

## 一、两种接法，先看 schema

子图就是一个被当节点用的图。接进父图只有两种方式，判断标准很干脆：**父子有没有共享的 state key。**

有共享 key，直接把编译好的子图丢给 `add_node`，子图会读写父图同名的 channel，不需要任何包装。多 agent 系统里常见的 `messages` 就属于这种：大家共用一个消息列表，只是各自往里面写。

```python
builder = StateGraph(ParentState)
builder.add_node("node_1", node_1)
builder.add_node("agent", subgraph)     # 共享 messages，直接插
builder.add_edge(START, "node_1")
builder.add_edge("node_1", "agent")
```

没有共享 key，就别硬插，包一层函数做映射。父状态取哪个字段喂给子图、子图返回哪个字段写回父图，全由你决定，这才是真正意义上的"隔"。

```python
def call_subgraph(state: ParentState):
    out = subgraph.invoke({"bar": state["foo"]})   # 父 → 子
    return {"foo": out["bar"]}                      # 子 → 父
```

第二种写法看着多一层，但边界干净：子图的内部字段（比如 `bar`、`baz`）根本不会漏到父状态里，父图也不需要知道子图内部怎么排布。团队分工时，这层映射就是接口契约。

## 二、隔得干不干净，看持久化

状态接好了，下一个问题是数据留不留。子图 `.compile()` 的 `checkpointer` 参数有三个值，行为完全不同，这是本篇最容易配错的地方。

| 档位 | 写法 | 行为 |
|---|---|---|
| 每次调用（默认） | `None` | 每次从新起点开始，单次调用内继承父图检查点，支持中断 |
| 按 thread | `True` | 同一 thread 上累积，下次接着上次继续 |
| 无状态 | `False` | 完全没有检查点，像普通函数，不能中断也不能续跑 |

```python
sub = builder.compile()                      # 默认：每次调用新起点
sub = builder.compile(checkpointer=True)     # 按 thread 累积
sub = builder.compile(checkpointer=False)    # 无检查点，纯函数
```

默认这一档最常用，也是多 agent 的主流姿势：客服问一次订单、查一次物流，本来就不该记得上一轮。它在单次调用内仍然能 `interrupt()`，因为父图的 checkpointer 会借给它用。

`True` 适合另一种场景：研究员 agent 需要跨几轮攒上下文，或者代码助手要记住改过哪些文件。但代价马上就来——**按 thread 的子图不支持并行调用**。模型一次发起两个针对同一个子图的工具调用，两边写同一个命名空间，检查点就撞了。官方给的解法是用 `ToolCallLimitMiddleware` 把该工具限成一次，或者在模型层关掉并行工具调用。

## 三、多个子图同名，状态会串

还有一个隐蔽的坑：当你同时挂几个按 thread 的子图，它们各自需要独立的存储空间，这叫命名空间隔离。

在节点里直接 `invoke` 的子图，命名空间是按**调用顺序**分配的：第一个、第二个。听着没问题，但你哪天调整了调用顺序，状态就跟着换了主人——水果专家突然读到了蔬菜专家的历史。

修法很朴素：给每个子 agent 包一层 `StateGraph`，节点名唯一，命名空间就稳定了。

```python
def create_sub_agent(model, *, name, **kwargs):
    agent = create_agent(model=model, name=name, **kwargs)
    return (
        StateGraph(MessagesState)
        .add_node(name, agent)      # 名字唯一 → 命名空间稳定
        .add_edge("__start__", name)
        .compile()
    )
```

而用 `add_node` 直接挂上去的子图，命名空间本来就跟着节点名走，不需要这层包装。这个差别值得记一下，省得白包一层。

## 四、想看子图里发生了什么

开了持久化，就能查子图状态：`graph.get_state(config, subgraphs=True)`，从 `tasks[0].state` 拿当前那层的数据。默认档拿到的是本次调用的状态，按 thread 档拿到的是累积后的状态。

```python
snapshot = graph.get_state(config, subgraphs=True)
sub_state = snapshot.tasks[0].state
```

但有个前提常被忽略：LangGraph 必须能**静态发现**这个子图，也就是它要么被 `add_node` 挂上，要么在节点函数里被调用。如果你在**工具函数**里 `invoke` 子图（subagent 最常见就是包成工具），`get_state` 就看不到它。中断倒是照样能冒到顶层图。

所以别把"查不到状态"当成 bug，先确认子图是怎么接进来的。要看执行过程，用 `stream.subgraphs` 更直接，`graph_name` 和 `path` 都是现成的。

## 五、handoff 不是隔，是换人接着聊

前面说的都是 subagent 模式：主 agent 调工具，工具里跑一个子 agent，结果回到主 agent，再由主 agent 对用户说话。隔离强、能并行，但用户始终只跟主 agent 对话。

handoff 是另一种：工具直接改状态里的 `active_agent`，控制权交给另一个 agent，**由它直接面对用户**。连续多轮时它更省——第二轮不用再走一次"转接"，因为人已经在那个 agent 上了。官方给的对比很直白：单次请求 subagents 要 4 次模型调用，handoff 只要 3 次；重复请求 handoff 第二轮回 2 次，subagents 还是 4 次。

代价是 handoff 串行，跨领域并行研究这种活儿它干不了。

## 六、跳图要带哪两条消息

多子图 handoff 的关键细节在消息配对。子图的工具里要跳回父图，用 `Command(graph=Command.PARENT, goto=...)`；同时必须带上两条消息：触发这次调用的 `AIMessage`，和一条补上的 `ToolMessage`。

```python
@tool
def transfer_to_sales(runtime: ToolRuntime) -> Command:
    last_ai = next(m for m in reversed(runtime.state["messages"])
                   if isinstance(m, AIMessage))
    return Command(
        goto="sales_agent",
        graph=Command.PARENT,
        update={
            "active_agent": "sales_agent",
            "messages": [last_ai, ToolMessage("已转接销售", tool_call_id=runtime.tool_call_id)],
        },
    )
```

为什么非得补 `ToolMessage`：模型发起工具调用，就期待一条对应 `tool_call_id` 的回复。少了它，对话历史就是残缺的，接手的 agent 一读就懵。

也别顺手把整个子图历史都塞过去。官方明确建议只传这一对，需要背景就在 `ToolMessage` 里写摘要——把子 agent 的内部推理全倒给下一个 agent，既贵又容易带偏。

还有个更省事的做法：单 agent 加中间件，用 `wrap_model_call` 按 `current_step` 换提示词和工具，根本不涉及跨图跳转。多数 handoff 场景这样写就够，只有确实需要独立图结构（反思、检索这类）时才拆多子图。

## 七、怎么选，一句话版

要强隔离、要并行、要主 agent 统一对外，用 subagent：子图包成工具，默认 `checkpointer=None` 每次新起点。

要连续对话、要按步骤解锁能力（先问保修再给方案），用 handoff 或单 agent 中间件，状态里放一个 `current_step`。

只做分流、不需要多轮记忆，用 router；知识太多但不想拆图，用 skills 按需加载。这几种官方都在同一张对比表里，指标是模型调用次数和 token 量，不是"看起来专业"。

## 八、一句话收尾

**子图隔的是上下文，不是责任。** 隔开之后，父图仍然要为"传了什么进去、拿回了什么"负责，这层映射写含糊了，隔离就只是把 bug 藏得更深。

上线前我一般查三件事：共享 key 的那几个字段，父子两边语义是不是一致；按 thread 的子图有没有被并行调用；handoff 的消息对不对得上 `tool_call_id`。三条都过，多 agent 才算真跑起来了。
