# 第13篇：重试超时怎么配｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 13 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

前 12 篇一直在讲"图怎么搭、状态怎么走"。这一篇换个角度：**图跑起来出错怎么办**。外部接口会超时，模型会 429，网络会抖一下，这些都是常态而不是事故。LangGraph 给了三个旋钮，装在节点上就能用。

注意版本：节点级超时和 `error_handler` 要 `langgraph>=1.2`，本篇按 1.2.x 写。

## 一、三个旋钮，固定顺序

先看全景，三个机制各管一段：

- `retry_policy`：**要不要再试一次**，按异常类型和退避参数决定；
- `timeout`：**单次尝试最多跑多久**，超了就抛 `NodeTimeoutError`；
- `error_handler`：**重试都失败了怎么收场**，跑一段补偿逻辑。

它们串成一条固定链路：节点尝试 → 抛异常（包括超时）→ 重试策略判断 → 还有次数就再来一次 → 次数耗尽才轮到 `error_handler`。

这条顺序很关键：**error_handler 不会在第一次失败时触发**。想"出错立刻补偿"却配了重试，就会等满三轮才进 handler。两个旋钮是解耦的，什么时候重试、什么时候补偿，要分开想。

## 二、默认值已经能打，但要知道它躲什么

只写 `RetryPolicy()`，默认是：

| 参数 | 默认 | 含义 |
|---|---|---|
| max_attempts | 3 | 含首次，即最多再试 2 次 |
| initial_interval | 0.5 | 第一次重试前等 0.5 秒 |
| backoff_factor | 2.0 | 每轮间隔翻倍 |
| max_interval | 128 | 间隔上限 128 秒 |
| jitter | True | 加随机抖动，防同时重试打爆上游 |
| retry_on | default_retry_on | 哪些异常值得重试 |

`default_retry_on` 的思路是"重试环境问题，不重试代码问题"。`ValueError`、`TypeError`、`ImportError`、`NameError`、`SyntaxError`、`RuntimeError`、`OSError` 这些都不重试——重试一百次也还是同样的错。对 `requests` / `httpx` 只重试 5xx，4xx 不重试。

这个默认很适合作为基线。要改就写清楚意图：

```python
from langgraph.types import RetryPolicy, default_retry_on

def only_network(exc: BaseException) -> bool:
    if isinstance(exc, MyBizError):      # 业务错误不重试
        return False
    return default_retry_on(exc)

builder.add_node("call_api", call_api,
                 retry_policy=RetryPolicy(max_attempts=4, retry_on=only_network))
```

## 三、重试是 at-least-once，不是 exactly-once

这句要划重点：**重试是"整个节点函数从头再跑一遍"**。

检查点只在 super-step 边界写，不写在函数中间。所以第一次尝试失败时，它写进 state 的那部分**会被丢弃**，第二次从上一个已提交的状态重新开始。

但副作用不在这个边界里。付款、发信、写第三方库，这些动作一旦发生就发生了：

```text
attempt 1: 调支付接口 → 支付成功 → 进程崩了
attempt 2: 从头跑 → 又调一次支付 → 又成功了
```

所以节点的外部副作用必须幂等。做法是带幂等键，而且**这个键必须来自已经持久化的状态**：

```python
def charge_customer(state: State) -> dict:
    key = f"charge:{state['order_id']}"      # 从已提交状态推导，可复现
    provider.charge(customer_id=state["customer_id"],
                    amount=state["amount"], idempotency_key=key)
    return {"charged": True}
```

反面例子是在节点里 `uuid4()` 现生成：第一次没返回，键就没被存下来，重试会生成另一个键，等于没做幂等。

还有一条心态上的纪律：**上游可能已经成功但回执丢了**。本地没有记录，不等于事情没发生。这种情况要先查对方的操作状态，再决定补偿还是继续。

## 四、超时：硬墙钟和进度重置不是一回事

`timeout=` 可以给秒数、`timedelta`，或者 `TimeoutPolicy`：

```python
from langgraph.types import TimeoutPolicy

builder.add_node("call_model", call_model,
                 timeout=TimeoutPolicy(run_timeout=120, idle_timeout=30))
```

两个参数语义完全不同：

- `run_timeout`：本次尝试的硬上限，**从头计到底，不因任何活动重置**，适合"这个接口就是不该超过两分钟"。
- `idle_timeout`：**只在没有可观察进展时计时**，一有进展就重置。适合长任务——流式吐 token、分批处理，只要还在动就不算卡死。

默认 `refresh_on="auto"` 时，状态写入、流式输出、子任务调度、任何 LangChain 回调（模型 token、工具调用、链的起止）都算进展。想让判定更严格，设 `refresh_on="heartbeat"`，只认显式心跳：

```python
async def long_job(state: State, runtime: Runtime) -> State:
    for batch in fetch_batches():
        process(batch)
        runtime.heartbeat()          # 非 idle 超时场景下是空操作
    return {"done": True}
```

两个限制要记住：**超时只支持 async 节点**，给同步节点配 `timeout` 会在编译期被拒；阻塞 I/O 用 `asyncio.to_thread` 包一层再放进 async 节点。

另外，`Send` 可以带 `timeout`，给扇出的单条任务单独收紧时限：

```python
Send("process_item", {"item": item}, timeout=TimeoutPolicy(idle_timeout=15))
```

## 五、超时和重试天然能配合

超时会抛 `NodeTimeoutError`（带 `node`、`elapsed`、`kind` 三个信息，`kind` 区分是 idle 还是 run 触发），它**默认可重试**。

两者一起配就是开箱可用：每次新尝试超时时钟重置，上一次的写被清掉再重来。想在第二次尝试时换降级接口，用 `runtime.execution_info.node_attempt`：

```python
def my_node(state: State, runtime: Runtime) -> State:
    if runtime.execution_info.node_attempt > 1:
        return {"result": call_fallback_api()}
    return {"result": call_primary_api()}
```

这个字段没有重试策略时也有，默认值 1，所以判断逻辑可以常驻，不用为了它专门配重试。

## 六、error_handler：重试之后的收场

`error_handler` 挂在节点上，入参是 state 加一个 `NodeError`（两个字段：`node` 和 `error`）。它最有用的是能返回 `Command`，一边更新状态一边改道，这就是 Saga 式补偿：

```python
def payment_error_handler(state: State, error: NodeError) -> Command:
    return Command(update={"status": f"compensated: {error.error}"},
                   goto="finalize")
```

几条细规则：

- `interrupt()` 抛出的不是普通异常，走的是 `GraphBubbleUp`，**不会被 error_handler 接住**，也不会触发重试，图照常暂停；
- 每个节点最多一个 handler；handler 自己抛错会往上冒泡，等于没有 handler；
- 包了子图的节点，子图里未处理的异常会升到父节点，父节点的 handler 收到的是子图那个异常；
- 失败的来源会被写进检查点，进程崩了之后恢复，handler 看到的还是同一个 `NodeError`。

## 七、图级默认，省掉重复配置

节点多了以后，每个 `add_node` 都写一遍太啰嗦，用 `set_node_defaults` 一次配全：

```python
graph = (StateGraph(State)
         .set_node_defaults(retry_policy=RetryPolicy(max_attempts=3),
                            timeout=TimeoutPolicy(run_timeout=30),
                            error_handler=mark_failed)
         .add_node("fetch", fetch)
         .add_node("charge", charge, error_handler=refund)   # 单点覆盖
         .compile())
```

优先级清楚：**单个节点上写的覆盖图级默认**，默认在 `compile()` 时解析，调用顺序无所谓。

两个坑：默认的 `error_handler` 不会套在 handler 节点自己身上（否则会自我捕获），`cache_policy` 也不套 handler；更要注意 **`set_node_defaults` 不会传给子图**，每个图管自己的默认。

## 八、优雅停机：在 super-step 之间刹车

最后一层是"要下线了怎么办"。`RunControl` 配 `invoke(..., control=control)`，任意线程调 `request_drain()`：

```python
control = RunControl()
signal.signal(signal.SIGTERM, lambda *_: control.request_drain("sigterm"))
try:
    result = graph.invoke(inputs, config, control=control)
except GraphDrained as e:
    log.info("drained: %s", e.reason)
```

drain 是协作式的，只在 super-step 之间生效：**正在跑的节点会跑完，正在重试的循环会跑到成功或耗尽**，不会中途掐断。之后如果还有下一步，抛 `GraphDrained`，检查点已存，用同一个 `thread_id` 调 `invoke(None, config)` 就能续上。

节点内也能自查 `runtime.drain_requested`，提前返回一个轻量结果。要留个心眼：`request_drain()` 不会取消 asyncio 任务或杀线程，想有硬上限就得再自己叠一层超时和取消。

## 九、一句话收尾

三个旋钮的顺序是固定的，配的时候按这个顺序想：**这次失败值不值得再试 → 一次尝试允许跑多久 → 全失败之后谁负责收场**。

配错的典型症状也很固定：该补偿的等了三轮才补偿，该快速失败的反复重试打爆上游，该停机的节点跑到一半被强杀丢状态。三句话对一遍，基本就齐了。
