## 正文

# 第03篇：四个钩子位怎么用｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 03 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

第 02 篇看的是循环留下的数据。这一篇看谁在循环里动手脚。

答案只有一句：middleware。`create_agent` 把四步循环压成一个函数，所有定制都从钩子进去——加日志、改提示词、换模型、裁工具、拦请求、接工具错误，全在这几个位置上。

## 一、四个位置，六个钩子

先纠正一个常见说法。钩子不是四个，是六个；位置只有四个。

- **整个 agent 的开始与结束**：`before_agent`、`after_agent`，每次 invoke 各跑一次
- **每次模型调用前后**：`before_model`、`after_model`，循环几轮就跑几次
- **模型调用本身**：`wrap_model_call`，把这次调用整个包住
- **每次工具调用本身**：`wrap_tool_call`，同样包住

前四个叫节点式钩子，按顺序跑，负责"看"和"改状态"；后两个叫包裹式钩子，能决定这次调用到底跑不跑。

这个区分很实用。想记日志、想校验、想往 state 里写一个计数，用节点式；想重试、想短路、想换模型，用包裹式。

四个位置里，两个是"一次"，两个是"每次"。`before_agent` 和 `after_agent` 一次 invoke 只跑一遍，`before_model` 和 `after_model` 循环几轮就跑几遍。分不清这两个词，最容易出现的疑问就是"我的日志怎么只打了一条"。

位置放错，效果完全不同。同样是"往 messages 里加一条提醒"，放 `before_agent` 只加一次，放 `before_model` 每轮都加，聊到第五十轮，列表里全是重复的提醒，token 白烧。

## 二、节点式：看一笔，改一笔

节点式钩子的签名很朴素：`state` 进来，返回一个 dict 或 `None`。

```python
from langchain.agents.middleware import before_model, after_model, AgentState

@before_model
def log_prompt(state: AgentState, runtime):
    print(f"即将调模型，当前 {len(state['messages'])} 条消息")
    return None

@after_model
def log_answer(state: AgentState, runtime):
    print(f"模型回了：{state['messages'][-1].content[:40]}")
    return None
```

返回的 dict 会并进 state，走的是 reducer。所以返回 `{"messages": [AIMessage("...")]}`，效果就是往列表尾部加一条——和第 02 篇的规则完全一致，没有第二套机制。

多条 middleware 并存时，`before_*` 按注册顺序正序执行，`after_*` 逆序执行。像栈：先进的最后出。

装饰器写法适合单个钩子。要同时给同步和异步版本，就得用类：`AgentMiddleware` 子类里写 `before_model`，再加一个 `abefore_model`。流式场景走的是异步链路，只实现同步版会拿到降级行为。

返回 `None` 表示"这一笔我不改"，和返回空 dict 等价。别为了看起来显式而硬返回一个空对象，没有意义。

## 三、包裹式：调不调、调几次，你说了算

`wrap_model_call` 的签名是 `request` 加 `handler`。`handler` 就是"真正去调模型"那一步，你握在手里，可以调 0 次、1 次或 N 次。

- 调 0 次：缓存命中，直接返回上次的 `AIMessage`，一分钱不花
- 调 1 次：正常路径
- 调 N 次：失败重试、限流退避、主模型挂了换备用

```python
from langchain.agents.middleware import wrap_model_call, ModelRequest

@wrap_model_call
def retry_model(request: ModelRequest, handler):
    for attempt in range(3):
        try:
            return handler(request)
        except Exception as e:
            if attempt == 2:
                raise
            print(f"第 {attempt + 1} 次失败，重试：{e}")
```

`request.override()` 是另一半用途：每次调用前换模型、裁工具、改系统提示词。

```python
@wrap_model_call
def route_by_size(request: ModelRequest, handler):
    model = big_model if len(request.messages) > 20 else small_model
    return handler(request.override(model=model))
```

按上下文长度选模型、按用户权限裁工具、按租户拼接提示词，都在这一步完成。它比改 `create_agent` 的参数灵活，因为每次调用都能重新算。

缓存那条路要注意 key。用最后一条 `HumanMessage` 加工具签名做 key，别用整个消息列表——列表里每条都有 id，每次都不一样，缓存永远命中不了。

还有个容易混的点：`request.messages` 是"即将发给模型"的那份，可能已经被前面的 middleware 裁过；想读完整状态用 `request.state`。

代价也说清楚：wrap 里重试会重复计费，缓存要自己管失效。包一层不等于免费。

`wrap_tool_call` 是同一套结构，只是包的是工具。第 02 篇讲的工具报错处理，落点就在这里。

## 四、跳出去：jump_to

有些情况不该让循环继续：消息超过 50 条、token 预算用完、命中拦截规则。

节点式钩子返回一个 `jump_to` 就能改道：

```python
from langchain.agents.middleware import before_model, hook_config, AgentState
from langchain.messages import AIMessage

@before_model(can_jump_to=["end"])
def check_limit(state: AgentState, runtime):
    if len(state["messages"]) >= 50:
        return {
            "messages": [AIMessage("这轮先到这，我们换个话题继续。")],
            "jump_to": "end",
        }
    return None
```

三个目标：`end` 直接收尾，`tools` 跳过模型去跑工具，`model` 回到模型节点。

`can_jump_to` 是必须声明的，框架会校验你有没有跳去一个没声明的地方。这个设计不烦人，反而防止了手滑写出死循环。

`tools` 这个目标用得少但有用：某类请求已经能确定该调哪个工具时，跳过模型这一轮直接执行，省一次调用，也省一次不确定。

跳出去不代表收尾被跳过。`end` 的定义就是"跳到第一个 `after_agent` 钩子"，清理资源、写审计日志这类活儿照样执行。

## 五、自己的状态：state_schema

middleware 想在多轮之间记东西——调用次数、剩余预算、用户 id——就扩 state：

```python
class BudgetState(AgentState):
    model_calls: NotRequired[int]

@after_model(state_schema=BudgetState)
def count_call(state: BudgetState, runtime):
    return {"model_calls": state.get("model_calls", 0) + 1}
```

还有一种更省事的做法：只读配置走 `runtime.context`，要累积的计数才放 state。分清"一次性的输入"和"要留下来的状态"，后面能少改很多代码。

`invoke` 的时候把初值传进去，后面每个钩子都能读到。

这里有个坑：节点式钩子可以直接 return dict，包裹式不行。wrap 里改状态，要返回 `ExtendedModelResponse`，把 `Command(update={...})` 一起带回去。写错了不会报错，只是状态悄悄没更新——这类问题最难查。

还有个生命周期问题：这些字段接了 checkpointer 就跟着 thread 走，关掉 checkpointer 就只在单次 invoke 内有效。以为它在，其实早就没了，是另一类难查的问题（第 08 篇讲 thread 时会再回到这）。

## 六、顺序与冲突

多个中间件叠在一起，顺序是固定的：

- `before_*` 正序，先注册的先跑
- `after_*` 逆序，后注册的先跑
- `wrap_*` 嵌套，第一个包住后面所有

非 reducer 字段发生冲突时，外层赢。所以最关键的那个中间件要放在列表最前面——它既能最早拦住输入，也能最后拍板输出。

举个真实冲突：两个中间件都往 `trace_id` 写值，字段没声明 reducer，结果是外层覆盖内层。你以为在记录完整链路，其实只剩最后一跳，排查时越看越糊涂。

## 七、别自己造：内置清单

能用的内置中间件比想象中多：

- `SummarizationMiddleware`：上下文超限自动摘要（第 05 篇细讲）
- `HumanInTheLoopMiddleware`：敏感工具调用前停下来等人批（第 16 篇实战）
- `ModelCallLimitMiddleware`、`ToolCallLimitMiddleware`：调用次数与并发限额
- `PIIMiddleware`：手机号、邮箱等敏感信息脱敏
- `TodoListMiddleware`：给 agent 一套待办工具
- `FilesystemMiddleware`、`SubAgentMiddleware`：读写文件、派子任务，偏重，按需开

手写中间件最麻烦的不是主逻辑，是异步版本和异常路径。能用内置就先别自己写。

内置也有顺序讲究。摘要要放在裁工具之前，先压历史再挑工具；人审要放在限额之后，先确认还允许调用再问人。顺序反了，要么白压，要么白问。

## 八、这一圈记住三件事

第一，四个位置、六个钩子。节点式负责看和改状态，包裹式负责调不调、调几次。

第二，改行为用 `wrap + override`，改状态用 `state_schema`；wrap 里改状态记得走 `Command`。

第三，顺序就是语义。同一件事，放在 before 还是 after、列表前还是列表后，结果完全不同。
