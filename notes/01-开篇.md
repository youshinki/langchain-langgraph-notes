# 第01篇：LangChain 1.x 只留了一个 create_agent | LangChain/LangGraph 实战系列开篇

先看三条时间线。

2024 年 2 月，LangGraph 作为独立库发布。官方给的理由很直白：当时的 LangChain 管的是模型抽象和常见应用的高层封装，缺一层能精确控制流程的编排层。

2025 年 10 月，LangChain 1.0 发布，把所有链和 Agent 换成同一个入口：`create_agent`。老代码整包挪进 `langchain-classic`。

2026 年 11 月 11 日，`langchain` 到 1.5，`langgraph` 在 1.2 上。主包里能用的东西，两只手数得过来。

三年走完一个圈：先做厚，再拆薄，最后把薄的那层架到自己原来的底层上。这个系列讲的就是这个圈怎么转，以及转完之后，写 Agent 的方式变了多少。

## 一、1.0 到底删了什么

先摆事实。

以前要搭一个带工具的问答，得先想清楚用哪套抽象：`LLMChain` 还是 `SequentialChain`，要不要 `RouterChain`，记忆挂 `ConversationBufferMemory` 还是 `SummaryMemory`，最后再包一层 `AgentExecutor`。每一层都能配，每一层都有自己的一套参数。

1.0 之后，`langchain` 主命名空间只剩几组：`agents`（核心就一个 `create_agent`）、`messages`、`tools`、`models`、`embeddings`、`middleware`。其余全部搬去 `langchain-classic`。

搬走不是"暂时兼容"，是划清界限：classic 里那套链式写法还能跑，但新能力不会往那儿加。

官方给的理由只有一句：框架应该围绕 Agent 的核心循环组织，而不是围绕"能拼多少种链"。

这话不太好听，但确实是实情。那套链的组合能力，九成的项目只用其中一种：把检索结果拼进 prompt，调一次模型，拿回答案。为了覆盖剩下那一成，所有人都在为抽象层付学习成本。1.0 的选择是，先把这一成砍掉，需要的人自己去写。

## 二、为什么敢删：Agent 本来就是四步

敢删，是因为那堆链拆开看，都是同一个循环的不同切法。

循环只有四步。

第一步，把消息列表送给模型。

第二步，模型返回。两种可能：带 `tool_calls`，或者给最终答案。

第三步，有工具调用就执行，把结果作为 `ToolMessage` 追加进消息列表。

第四步，回到第一步。直到某一次模型不再调工具，循环结束。

RAG 是在第一步之前塞检索结果；摘要是在消息太长时压一压；人审是在第三步之前停一下；模型路由是在第一步换一个模型。它们全是往这四步的缝里插一刀。

插刀的接口起了个名字，叫 middleware。这也解释了 1.0 的主包为什么这么小：能力没有消失，只是从"并列的类"变成了"挂在同一个循环上的钩子"。

换句话说，1.0 做的事不是删 API，是把"组合"降级成"配置"。以前你靠继承和拼装搭出一条独一无二的链，现在你只能在四个位置上表态：进模型之前做什么、出模型之后做什么、整次模型调用怎么包、整次工具调用怎么包。表达力确实收窄了，但换来的是同一套代码在任何模型、任何场景下都能讲清楚"我插在哪"。

顺手给个最小例子。

```python
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model

model = init_chat_model("deepseek:deepseek-chat")   # 换 provider 只改这一行
agent = create_agent(
    model=model,
    tools=[search_docs, send_email],
    system_prompt="先查资料，再动笔。",
)
result = agent.invoke({"messages": [{"role": "user", "content": "整理本周的竞品动态"}]})
```

一个函数，一次 `invoke`。没有链，没有 executor，没有 memory 对象。

## 三、LangGraph 没被取代，是被藏到了下面

最容易误读的一点：`create_agent` 不是取代 LangGraph，它是编译出来的一张图。

底下干的事很朴素：建一个 `StateGraph`，两个节点——`model` 和 `tools`，一条条件边判断"还有没有 `tool_calls`"，有就回 `tools`，没有就 `END`，然后 `compile()`。

因为跑在图运行时上，四样东西是白送的。

检查点：每一个 super-step 结束落一次状态，给了 `thread_id`，会话就能接着聊。

流式：节点级更新、token、工具参数增量，都能取出来。

中断：节点里调 `interrupt()`，图停住等人，`Command` 回来继续。

时间旅行：历史检查点能翻，能 fork 出去走另一条路。

有个细节能看出这层关系。1.0 把流式事件里的节点名从 `agent` 改成了 `model`。因为图里真正干活的节点就是"调模型"和"跑工具"，"agent"是整个循环的名字，不是一个节点。名字对上了，你从流里捞到的每个片段才知道自己属于哪一步。

这也解释了 1.1、1.2 那批更新为什么全发生在 `langgraph` 而不是 `langchain`：`version="v2"` 的类型化流、`DeltaChannel` 只存增量、`add_node(timeout=...)`、`error_handler=`、`RunControl.request_drain()`。全是运行时的事，上层只负责享受。

那什么时候该掀开盖子，直接写 `StateGraph`？三个信号：流程有明确分支和并行、需要子图隔离上下文、或者根本不是聊天——比如一条"抽取、校验、入库"的固定流水线。第 06 篇开始专门讲这个。

## 四、收敛的代价：定制只剩两个出口

抽象变薄是要付账的。

第一笔，状态只能是 `TypedDict`。想拿 Pydantic 类当图状态？不行，得绕。

第二笔，预绑定模型不支持了。`model.bind_tools(...)` 那种写法在 v1 里不再是最优路径，动态换模型要走 middleware。

第三笔，参数改名。`create_react_agent` 时代的 `prompt`、`pre_model_hook`、`post_model_hook` 换了位置，照着老博客抄，第一行就报错。

出口只有两个。

一个是 middleware。`before_model`、`after_model`、`wrap_model_call`、`wrap_tool_call`，四个位置，覆盖"调用之前""调用之后"和"整段包裹"。摘要、重试、人审、动态提示词，都能塞进去。第 03 篇把这张钩子矩阵拆开讲。

另一个是 1.5 新加的 decisions。`BaseDecisionModel` 把"要不要走这条"变成一个可校验的判定：二选一、分类、打分、框选四种题型。架在上面的 `ModelRouterMiddleware` 负责选模型，`AutoModeMiddleware` 负责拦危险工具调用。不再是往 prompt 里堆"你必须先……"，而是让判定模型给出一个能验的结论。

这两个出口听上去窄，但能力一点没少。举个具体的：1.4.6 给 `HumanInTheLoopMiddleware` 加了 `interrupt_mode="per_call"`。以前一次批里几个工具调用只抛一个中断，人在页面上一次批完；现在每个调用各抛一个，按中断 ID 逐个回答，每个中断还带 `response_schema`，客户端能照着 schema 直接把表单画出来。这类改进正好落在 middleware 这个口子上——位置没变，往里塞的东西变细了。

这两个出口之外，就没了。所以这个系列的重点不是"有哪些 API"，而是"定制该落在哪个位置"。

## 五、这个系列怎么走

18 篇，四个阶段。

一、LangChain 1.x 重做之后（01-05）：循环、middleware 钩子矩阵、工具与结构化输出、模型层与路由降级。

二、LangGraph 运行时（06-11）：State / Reducer / Channel、条件边与 `Send` 并行分发、checkpointer 与 super-step、interrupt 的真实语义、流式协议、子图与多 Agent。

三、工程化（12-15）：时间旅行与调试、重试与超时与优雅停机、可观测与评估、部署。

四、实战（16-18）：一个带人审的资料整理 Agent、一个 supervisor 带子图的研究小组，最后一篇做选型复盘：LangChain、LangGraph、Deep Agents，以及我们拆过的 dsh，什么时候用哪个。

三条约定：代码锁 Python 3.11+；版本以 `langchain 1.5.0`、`langgraph 1.2.x` 为准；每篇一个能单独跑的目录，不依赖上一篇的中间状态。
