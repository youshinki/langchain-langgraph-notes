# 第15篇：从脚本到服务｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 15 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

前 14 篇都在本地跑：`graph.invoke()` 一调，结果就在终端里。可一旦要给别人用，问题立刻换了一批——谁常驻、状态存哪、并发怎么排队、前端怎么拿流。这一篇讲怎么把图交给 Agent Server，变成一个能接请求的服务。

## 一、脚本缺的不是 invoke，是四样东西

本地脚本能跑，是因为所有前提都由你的终端兜着。上线后这四件事没人替你兜：

1. **常驻进程**：脚本跑完就退出，服务要一直活着等请求；
2. **数据库**：`MemorySaver` 在进程里，重启即失忆，得换成 Postgres；
3. **任务队列**：十个请求同时进来，谁先跑、谁排队、谁被取消；
4. **HTTP 接口**：前端不会调你的 Python 函数，它只会发请求、收 SSE。

Agent Server 就是这四样的打包：官方叫法是"workflow orchestration runtime"，对外暴露 assistants、threads、runs、crons 四组资源，内置持久化和任务队列。

所以部署一个 Agent，本质是部署三样东西：**图（代码）、数据库（Postgres）、队列（Redis 做信令，数据仍落 Postgres）**。Redis 只存短暂的调度与流事件，不存业务数据。

## 二、langgraph.json：一个文件说清交什么

CLI 默认读当前目录的 `langgraph.json`，`dev`、`build`、`up`、`dockerfile` 全用它。最小的一份长这样：

```json
{
  "$schema": "https://langgra.ph/schema.json",
  "python_version": "3.12",
  "dependencies": ["."],
  "graphs": {
    "agent": "./src/agent/graph.py:graph"
  },
  "env": ".env"
}
```

四个键记住就够用：

- `dependencies`：写 `"."` 表示用当前目录的包声明，也可以写 `requirements.txt` 所在的目录路径，注意别把文件名本身写进去；
- `graphs`：图 ID 到代码位置的映射，`agent` 这个名字后面就是调 API 时用的 `assistant_id`；
- `env`：`.env` 路径，或直接写成键值映射；
- `python_version`：`3.11` / `3.12` / `3.13`，默认 3.11。

再往上有 `dockerfile_lines` 补 Dockerfile 行、`checkpointer` 选后端（默认 Postgres，也可 mongo 或自定义）、`store` 配语义检索与 TTL、`auth` 挂鉴权、`http` 加自定义路由和 CORS。这些是有了明确需求才动的旋钮，第一天别全打开。

## 三、dev 和 up 差在哪

两条命令都起服务，定位完全不同：

| | `langgraph dev` | `langgraph up` |
|---|---|---|
| Docker | 不需要 | 需要 |
| 装法 | `pip install "langgraph-cli[inmem]"` | `pip install langgraph-cli` |
| 默认端口 | 2024 | 8123 |
| 状态存哪 | 本地目录 | 自带 Postgres 容器 |
| 用途 | 开发调试、热重载 | 接近生产的验证 |

```bash
langgraph dev                       # 内存版，改代码自动重载，附带 Studio
langgraph dev --tunnel              # 给远程前端一个公网隧道
langgraph up --port 8000 --wait     # Docker Compose，含 Postgres
langgraph build -t my-agent:v1      # 只出镜像，不启动
```

`dev` 是"能跑就行"的那一档：状态落本地目录，重启不丢，但也不适合压测。`up` 会把 `langgraph-api` 和 Postgres 一起拉起来，端口、镜像、外部库都能指定，本地就能预演部署。CLI 目前只支持 Python 3.11 以上——这条是硬门槛，不是建议。

## 四、图怎么交出去：编译实例优先

`graphs` 指向的东西有两种写法，差别在于编译时机：

```python
# src/agent/graph.py
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model="openai:gpt-5",
    tools=[search_docs],
    checkpointer=InMemorySaver(),   # 仅本地跑通时用，部署时删掉
)
graph = agent                          # 直接导出编译好的图
```

- **导出已编译的图**（推荐）：容器启动时加载一次，所有请求复用，没有每请求编译开销；
- **导出工厂函数**：`def make_graph(config): ...`，服务每次需要图时调用一次，适合按 assistant 配置换模型、换工具的场合。方便，但每次调用都要付编译成本。

还有个容易踩的坑：**checkpointer 和 store 由服务端注入**，不要在图代码里自己配。部署环境的数据库连接、TTL、序列化策略都归服务管，你写死一个 `PostgresSaver` 只会和平台打架。本地调试才用 `InMemorySaver`，上线前记得摘掉。

## 五、assistant：同一个图的不同人格

部署完成后，服务会为 `graphs` 里的每个图自动建一个**默认 assistant**。assistant 不是新图，它是"图 + 一份配置"的实例：同一个图结构，可以挂多个 assistant，各自带不同的 prompt、模型、工具集。

调用时传 `graph_id`（如 `agent`）走默认 assistant，传 assistant 的 UUID 走指定配置。修改 assistant 会自动生成新版本，能提升也能回滚；注意更新是全量覆盖，不做字段合并，改之前把完整配置带上。

这条能力只在 Agent Server 上有，开源库里没有 assistant 这个概念。很多人第一次部署后困惑"我的 config 去哪了"，答案就是它被 assistant 接走了。

## 六、thread 和 run：状态推进的最小单位

服务端的调用链是三段：建 thread、起 run、等结果。

```python
from langgraph_sdk import get_client

client = get_client(url="http://127.0.0.1:2024")
thread = await client.threads.create(metadata={"user": "u_1024"})

run = await client.runs.create(
    thread["thread_id"],
    "agent",
    input={"messages": [{"role": "user", "content": "帮我查下退款政策"}]},
)
await client.runs.join(thread["thread_id"], run["run_id"])   # 等到跑完
state = await client.threads.get_state(thread["thread_id"])   # 取最终状态
```

`runs.create` 返回的是 `status: pending`，它在队列里，不在执行中。想同步拿结果就 `join`，想看过程就换 `runs.stream` 拿事件流。不需要记忆的一次性任务走 stateless run：不建 thread，跑完即弃。

有个约束必须记住：**同一条 thread 上，同一时刻最多只有一个 run 在跑**。这是队列层强制的，不是你代码里加锁加的。理解这一点，后面并发和双击的问题都好推。

## 七、同一线程来了第二条消息

用户在 Agent 干活的中间又发了一句，这就是 double texting。服务端给了四种策略，选哪个取决于你的产品语义：

- `enqueue`（默认）：排队，等当前 run 结束再顺序执行，不丢消息；
- `reject`：直接拒掉，返回冲突错误，当前 run 不受影响，客户端自己提示"请稍等"；
- `interrupt`：打断当前 run，保留已完成的进度，新输入从这个状态继续——适合"补充说明"，但要求你的图能处理半截的工具调用；
- `rollback`：打断并回滚，连原始输入一起作废，新消息当全新一轮跑——适合"我说错了，重来"。

```python
run = await client.runs.create(
    thread["thread_id"], "agent", input=correction,
    multitask_strategy="rollback",
)
```

没有全局默认可设，每次 `runs.create` 都得显式表态。默认值 `enqueue` 在聊天场景里最不容易出事，但它意味着用户会看到"上一条先答完"。

## 八、cron 与后台任务

要按点跑的任务不用自己写调度器，`crons` 客户端直接排：

```python
await client.crons.create_for_thread(
    thread["thread_id"],
    "agent",
    schedule="0 9 * * *",            # 每天 9 点，cron 表达式
    input={"messages": [{"role": "user", "content": "今天的待办汇总"}]},
    timezone="Asia/Shanghai",
)
```

`create_for_thread` 复用同一条 thread，历史越攒越厚；`crons.create` 每次新建一条 thread，每次输入相同、互不污染。周报、巡检、每日摘要这类场景，后者通常更合适。

后台长任务还有两个配套：run 完成时可以打 webhook 回调；持久化频率由 durability 控制，`async`（默认）每步写完，`exit` 只存最终状态。队列侧每个 worker 默认并发 10 个 run（`N_JOBS_PER_WORKER`），这个数限的是执行并发，不是 API 请求数——API 服务器只接请求、不跑图，两者可以分开扩。

## 九、一句话收尾

部署形态按体量选：**单机**（API 自己管队列，自托管默认）、**API 与队列分离**（`queue.enabled: true`，两层各自扩）、**分布式运行时**（编排与执行再拆开，扛高并发）。

落到云上还有三种：LangSmith Cloud 托管、Hybrid（控制面在云、执行在你自己的机器）、完全自托管。自托管若是不带控制面的 standalone 形态，数据库和 Redis 都得你自己给，连接串通过 `DATABASE_URI`、`REDIS_URI` 传进去。

一句话记：**脚本到服务，不是加个 FastAPI 就完事，是把状态、队列、身份和接口四件事交给别人托管，自己只管图里的那点逻辑。**
