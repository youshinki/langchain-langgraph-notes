# 第09篇：中断为什么要重放｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 09 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

第 08 篇讲了断点续跑，这一篇讲它最尖锐的那部分：人审。`interrupt()` 看着像"暂停"，实际机制是"抛异常 + 整段重跑"。不理解这一点，人审流程一定能写出重复扣款、重复发邮件。

## 一、interrupt 不是 return，是抛异常

在节点里调用 `interrupt()`，框架做的是三件事：抛出一种特殊异常把执行掐断、用 checkpointer 把当前状态存下来、把载荷交给调用方。

```python
from langgraph.types import interrupt

def approval_node(state):
    approved = interrupt("这单 500 块，批不批？")
    return {"approved": approved}
```

第一次跑，你会在 `result["__interrupt__"]`（或用事件流时的 `stream.interrupts`）里拿到这句话。图就此停住，等你。

这里的第一条纪律：**别把 `interrupt()` 包在 `try/except` 里**。它就是靠这个异常停机的，你一 catch，中断就不会传回图，流程直接跑飞。要 catch，只 catch 你自己的业务异常，且范围别盖住它。

顺便区分两个容易混的东西：编译期的 `interrupt_before` / `interrupt_after` 是**静态断点**，固定卡在某个节点前后，适合调试时一步步看；`interrupt()` 是**动态中断**，写在代码任意位置、可以按状态决定要不要问。做人审用后者，前者只当日志断点。

## 二、续跑靠同一个 thread 和一个 resume 值

继续执行只有一种姿势：

```python
graph.invoke(Command(resume=True), config)
```

`resume` 的值会成为那次 `interrupt()` 调用的返回值。所以上面那个节点，`approved` 拿到的是 `True`，而不是重新问一遍。

条件是 `thread_id` 必须和中断时一样：它是指针，指错了就指到另一根线上。`Command(resume=...)` 也是唯一适合当 `invoke` 输入的 Command 形态，别的参数是给节点返回用的。

中断期间，状态是能看的：`graph.get_state(config)` 会给你 `values`、`next`，`tasks` 里还挂着待处理的中断。这一点在排查"为什么它没停"时很有用——先看 `next` 里到底有没有待执行节点。

## 三、重放：续跑是从函数开头重来

关键在这句：恢复执行时，运行时**把整个节点从头再跑一遍**，不是从 `interrupt()` 那一行接着往下。

于是：

```python
def node_a(state):
    db.create_audit_log(user_id=state["user_id"], action="pending")  # 每次重跑都插一条
    approved = interrupt("批不批？")
    return {"approved": approved}
```

第一次跑插一条，人工批准后重跑又插一条，再拒绝、再改主意，条数继续涨。这不是 bug，是机制：框架没有"断点行号"，只有"重新执行这个节点"。

明白这一点，"为什么文档反复强调幂等"就不用背了——因为你的节点注定会被执行多次。

它和上一篇的 pending writes 还有一层关系：同一 super-step 里其他成功节点不会重跑，只有这个被打断的节点整个重来。所以重放的影响面被框在"一个节点内"，而不是整张图。这也解释了为什么把副作用拆到独立节点那么值得——拆得越细，重放波及的范围越小。

## 四、副作用的三条摆法

正确写法有三种，按场景挑：

```python
# ① 前置副作用必须幂等：用 upsert，而不是 insert
def node_a(state):
    db.upsert_user(state["user_id"], status="pending_approval")
    approved = interrupt("批不批？")
    return {"approved": approved}

# ② 副作用放到 interrupt 之后，批准了才执行
def node_a(state):
    approved = interrupt("批不批？")
    if approved:
        db.write_audit(state["user_id"], "approved")
    return {"approved": approved}

# ③ 干脆拆节点：一个只管问，一个只管做
def approval_node(state):
    return {"approved": interrupt("批不批？")}
```

第三种最干净：审批节点没有副作用，执行节点做幂等写入，图上看得出"人审在哪儿"。

还有一种常被忽略的错误示范：在 `interrupt()` 之前往列表里 append 一条"已申请审批"的历史。看着无害，重跑三次就是三条。列表类状态能交给 reducer 累积，但外部存储不会自动帮你合并，重复就是重复。

要注意第二种也不是万能的：节点在副作用之后、返回之前挂掉，重试照样会重复。真正的保险永远是"外部系统能去重"，比如唯一键、幂等 token。

## 五、载荷要能渲染，回复能被校验

`interrupt()` 的载荷可以是任何可 JSON 序列化的东西。它不只是给日志看的，前端要靠它渲染审批卡片，所以别塞一坨内部对象，写清楚"问什么、涉及什么"。

从 langgraph 1.2.12 起，还能给 `response_schema`，把人工回复按 Pydantic 模型校验：

```python
from pydantic import BaseModel

class Decision(BaseModel):
    approved: bool
    note: str | None = None

def approval_node(state):
    decision = interrupt({"question": "批不批？", "amount": 500}, response_schema=Decision)
    return {"approved": decision.approved, "note": decision.note}
```

给了 schema，`interrupt()` 返回的是校验后的对象；传错值会抛 `ValidationError`，你可以在同一个 thread 上重发一个正确的 `Command(resume=...)` 再来一次。这比"人工填错、流程带着脏数据往下跑"好太多。

注意这里依然是重放：重发一次，节点又从头跑一遍，`interrupt()` 之前的代码再执行一次。所以"能校验"不等于"能随便重试"，幂等那条线还是得守住。

## 六、多个中断：序号必须稳定

一个节点里可以有多个 `interrupt()`。恢复时，框架拿节点任务里存的那串 resume 值，**按索引** 和中断一一配对——第一个中断配第一个值，第二个配第二个。

这意味着顺序必须每次一致：不能这次跳过第一个、不能按条件增删中断、更不能 `while True` 里循环调它。校验类需求的标准做法是"一个节点只问一次"，用条件边回环重问，而不是在节点里循环。

如果多个并行分支同时中断，续跑时用一个映射把每个中断的 `id` 对上值：

```python
resume_map = {i.id: f"answer for {i.value}" for i in stream.interrupts}
graph.stream_events(Command(resume=resume_map), config, version="v3")
```

用 `id` 而不是位置，并行场景才不会张冠李戴。

## 七、工具里也能中断

`interrupt()` 可以写在工具函数里，等于"这个工具被调用时先问一句"。批准后还能顺手改参数——用户在审批卡里把收件人改了，工具就用改过的值执行。

```python
@tool
def send_email(to: str, subject: str, body: str):
    """发邮件。"""
    resp = interrupt({"action": "send_email", "to": to, "subject": subject})
    if resp.get("action") != "approve":
        return "已取消"
    return f"已发送给 {resp.get('to', to)}"
```

好处是审批逻辑跟着工具走，换到别的图里也能用；代价是这个工具从此依赖 checkpointer 和 thread，不能再当普通函数随手指调用。

## 八、一句话收尾

`interrupt()` 的真实语义是：**停机、存状态、等你给一个值；续跑时把节点从头重放，让那次调用直接返回这个值**。

所以设计人审不是设计"暂停界面"，是设计"重放安全"。判断标准很朴素：这个节点被跑三遍，账还对得上吗？对得上，就可以上人审；对不上，先把它拆开。

上线前我会做一次很土的自测：连点三次批准、再连点两次拒绝，然后去数据库数记录。数量对、状态对，才敢放行。这个测试不测代码逻辑，专测重放安全——而重放恰恰是最容易被"本地跑通了"掩盖的问题。
