# 第12篇：回到上一步重走｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 12 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

第 08 篇讲断点续跑，第 09 篇讲中断重放，这一篇把两个话题合起来：既然每一步都存了检查点，那能不能**退回某一步，换条路再走一遍**？答案是可以，而且有两种走法，语义差别很大。

## 一、重走不是回滚

LangGraph 把这件事叫 time travel，底层全靠 checkpoint。官方区分两个动作：**replay**（从旧检查点原样重跑）和 **fork**（从旧检查点改状态后分叉）。

两者有个共同前提：**检查点之前的节点不重跑**，结果已经存下来了，直接复用；**检查点之后的节点全部重跑**，包括模型调用、外部 API、`interrupt()`。这句话要读两遍——重放不是"读缓存回放录像"，是真刀真枪再执行一次，模型可能给出不一样的答案，接口可能第二次扣钱。

所以第 09 篇那条纪律在这里同样成立：能重走的图，副作用必须幂等。时间旅行不是时光机，是"再来一遍"。

## 二、先找到那个点

历史是按 thread 存的，一条 thread 一串检查点。取法就一句：`get_state_history(config)`，注意它是**逆序**的，最新的在最前面。

```python
history = list(graph.get_state_history(config))
for s in history:
    print(s.next, s.config["configurable"]["checkpoint_id"])
```

怎么定位想回到的那一步？不要背 checkpoint_id，用 `next` 判断更稳：`next == ("write_joke",)` 表示"这个检查点之后该跑 write_joke 了"。也就是说，这个快照正好停在 write_joke 之前，拿它重走就会从 write_joke 开始。

`next` 为空元组，说明这是终态，后面没活儿了。

还有两个细节：`snapshot.config` 里不只有 checkpoint_id，thread_id 也在里面，两个一起传才是"同一条线回到某一步"；如果只改 checkpoint_id、thread 对不上，运行时找不到那条历史，行为会变成从当前最新状态继续，看起来像"没生效"。

## 三、replay：原样再走一遍

重放只有一行，输入给 `None`，配置换成那个快照的 config：

```python
before_joke = next(s for s in history if s.next == ("write_joke",))
graph.invoke(None, before_joke.config)
```

`None` 是关键：不给新输入，让运行时从检查点往后接着跑。前面 `generate_topic` 的结果直接沿用，不会重新生成；`write_joke` 会老老实实再执行一次。

有个边界条件官方专门写了：**从终态检查点重放是空操作**，因为没有 `next` 节点可跑。所以别指望"重放最后一次能刷新结果"，要变就得往前退一步。

## 四、fork：改完再走，历史不删

fork 多一步 `update_state`：在旧检查点上改状态，运行时给你生成一个新检查点，从那儿分叉。

```python
fork_config = graph.update_state(before_joke.config, values={"topic": "chickens"})
result = graph.invoke(None, fork_config)
```

这里最容易误解的一句：**`update_state` 不回滚 thread**。它只是从指定点长出另一条分支，原来的执行历史一条不少地留着。所以你可以在同一条 thread 上摆好几个"如果当时……"的版本，对比它们各自的终局。

这对调试特别有用：线上那次跑歪了，把输入改一改重走，看是新提示词的问题还是模型抽风，不用另开 thread 重造一遍现场。

但对比实验要留个心眼：模型本身有非确定性，同一条分支重走两次也可能不同。想判断"是改动的功劳还是随机"，同一组参数至少跑三遍，或者把温度调到 0 再比。

```python
fork_config = graph.update_state(
    before_joke.config,
    values={"topic": "chickens"},
    as_node="generate_topic",     # 有并行分支时显式声明
)
```

## 五、as_node 什么时候必须写

`update_state` 改的值会走目标节点的 writer（包括 reducer），检查点会记成"这个节点产出的"，然后从它的后继继续。默认情况下运行时能从版本历史推断出是哪个节点，从具体检查点 fork 时通常都对。

但三种情况必须自己写 `as_node`：

- 并行分支：同一个 step 里多个节点都改了状态，运行时判断不出最后是谁，直接抛 `InvalidUpdateError`；
- 新 thread 造状态：还没有任何执行历史，常见于测试里预置一个初始现场；
- 想跳过节点：把 `as_node` 指到更靠后的节点，图就认为那个节点已经跑过了。

第三种的用法要小心，它本质是在"谎报进度"，语义上等价于手工构造状态，别拿它掩盖本该修的流程。

## 六、重走必然再撞上 interrupt

人审图做时间旅行，行为很直接：**中断会被重新触发**。含 `interrupt()` 的节点重跑，跑到那行又停下来，等你给一个新的 `Command(resume=...)`。

```python
graph.invoke(None, before_ask.config)          # 停在中转，等新答案
graph.invoke(Command(resume="Bob"), fork_config)
```

多步表单的场景更值钱：姓名、年龄各问一次，你想只改年龄，那就 fork 在两次中断**之间**——姓名那步的结果保留，年龄重新问。不用把用户已经答过的问题再问一遍，这是 time travel 在实际产品里最像"功能"的地方。

## 七、子图里能退多细

粒度取决于子图有没有自己的 checkpointer。

默认情况子图继承父图的检查点，父图把整个子图当成**一个 super-step**：只有父层的一份检查点。于是你只能退到子图之前，一退就是整个子图从头重跑，进不到子图内部两个节点之间。

```python
subgraph = builder.compile(checkpointer=True)   # 子图自己存历史
sub_config = graph.get_state(config, subgraphs=True).tasks[0].state.config
fork_config = graph.update_state(sub_config, {"value": ["forked"]})
```

给子图 `checkpointer=True`，它就有了自己的检查点历史，才能精确到"子图里 step_a 之后、step_b 之前"。代价是检查点变多、存储变大，这也是第 11 篇讲过的三档持久化在时间旅行上的直接投影。

顺带说清一件事：时间旅行的可用粒度，等于检查点的粒度。父层只有一份，就别指望能退到子图内部的某一步；反过来，检查点存得越细，能做的实验越精细，成本也越高。这个权衡应该在设计阶段定，不是等出问题再补。

## 八、一句话收尾

时间旅行是调试和实验工具，不是产品功能——除非你确实要做"改答案重算"这种交互。

用之前先问三句：这一步之后的副作用幂等吗？退回去重跑，外部系统会不会二次扣款？检查点存了这么多，存储和清理策略定了吗？

三条都答得上来，再把它接进流程。否则它就是个放大 bug 的按钮：原本只错一次的地方，被重走三次。

真要做成产品功能，还得再补两层：一是把每个检查点和可见的"步骤名"对上，别让用户面对一串 checkpoint_id；二是给重走加审计，谁在什么时候退了哪一步、改了什么，都要留痕。毕竟对业务方来说，"改历史"比"跑错了"更难解释。
