# 第07篇：一张图怎么分叉｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 07 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

上一篇把 state 的合并讲完了，这一篇讲"走到哪"。节点干完活，图要知道下一步去哪：有时是固定的一条边，有时要看状态决定，有时要同时改状态和改路线，有时要按列表长度扇出。这四种情况用三样东西解决。

## 一、边只干一件事：决定下一步

节点负责干活，边负责指路。默认的边是静态的：`add_edge("a", "b")`，永远从 a 到 b。

如果这个节点有两条静态出边，那么 b 和 c 会在下一个 super-step **并行**跑。这不是"先 b 后 c"，是同一时刻两条分支都激活，各自读到同一份旧状态。

理解了这点，后面所有分叉都只是"谁来决定这些出边"。

再补一个时序细节：并行分支读的都是这一轮开始时的同一份状态，各自算完的更新会在 step 结束时统一合并。所以分支之间看不到对方的中间结果，别在 B 里指望 A 刚写的值——那要等下一个 step。

## 二、条件边：给路由函数一份状态

要按状态决定去哪，用 `add_conditional_edges`。它接一个路由函数，函数拿到当前 state，返回下一个节点的名字。

```python
from langgraph.graph import END, START, StateGraph

def route(state):
    if state["need_search"]:
        return "search"
    return END

graph.add_conditional_edges("plan", route)
```

路由函数可以返回三种东西：节点名、`END`、节点名列表。返回列表就是扇出，列表里的节点在下一个 super-step 并行跑。

它应该是个纯函数：只看 state，只给方向，不查库、不调模型、不写日志。很多人习惯在路由里顺手做一次判断性检索，结果这个函数被执行两遍，账单翻倍还查不出原因。

也可以传一张映射表，把函数的语义化返回值翻译成节点名：

```python
graph.add_conditional_edges(
    "plan",
    lambda s: "search" if s["need_search"] else "answer",
    {"search": "search", "answer": "generate"},
)
```

好处是路由函数可以返回 `"approve"`、`"reject"` 这种业务词，翻译交给表，未来改节点名不用动路由逻辑。

再补一个边界：路由函数返回的节点名如果拼错了，编译期查不出来，要到运行时才炸。吃了两次亏之后我习惯把节点名抽成常量，路由函数和 `add_node` 引同一份，改名时一起改。

## 三、入口也能分叉

`START` 是个虚拟节点，你同样可以对它挂条件边：

```python
graph.add_conditional_edges(START, lambda s: "fast" if s["short"] else "deep")
```

常见用法是按请求类型分流：闲聊走轻量链路，检索类走重链路。这比在第一个节点里写 if 更清楚，因为分叉本身画在图上了。

## 四、Command：改状态和指路合为一步

有些时候，下一步去哪，取决于你刚刚在函数里算出来的东西。分两步写就会别扭：节点先更新状态，再靠路由函数读刚写的值。

`Command` 把两件事合成一次返回：

```python
from typing import Literal
from langgraph.types import Command

def check(state) -> Command[Literal["fix", "done"]]:
    if state["score"] > 0.8:
        return Command(update={"status": "ok"}, goto="done")
    return Command(update={"status": "retry"}, goto="fix")
```

`update` 等同于普通节点返回，走 reducer；`goto` 等同于条件边的返回值。返回类型标注 `Command[Literal[...]]` 不是装饰，它告诉框架这个节点可能去哪些地方，图才画得出来。

还有一个必须守的规矩：**同一个节点不要同时挂静态边和 `Command`**。静态边照样会跑，等于多开一条你不知道的路径。要 `Command` 就只用 `Command`。

`Command` 另外两个用途可以先记着名字：从子图里跳到父图的节点，用 `graph=Command.PARENT`；在工具里返回 `Command` 也能改状态、指路。这两件事后面讲子图和多轮 agent 时会再碰。

## 五、Send：同一个节点跑 N 次

前面三种分叉，跑的还是"每个节点一次"。真正需要"按列表长度扇出"时，用 `Send`。

`Send` 从条件边返回，每个 `Send` 带一个目标节点和一份自定义输入。框架按返回的个数启动 N 个并行实例，每个实例拿到的是你塞进去的那份小状态，而不是整张图的 state。

```python
from langgraph.types import Send

def fan_out(state):
    return [Send("worker", {"item": x}) for x in state["items"]]

graph.add_conditional_edges("dispatch", fan_out)
```

这就是 map-reduce 的骨架：dispatch 拆任务，worker 并行跑，后面一个节点读汇总结果。worker 往共享 key 写时要靠 reducer 合并——上一篇讲的列表 reducer，在这里才真正派上用场。

`Send` 和普通边的差别要记住：普通边选的是"哪些节点下一轮跑"，被选中的节点仍然拿到完整 state，而且拓扑在建图时就固定了；`Send` 是运行期才知道要跑几次，每次可以喂不同输入。

代价也很直接：worker 拿到的是你塞的那份小状态，不是完整 state。需要全局配置就一并塞进 payload，或者放进 runtime context。塞少了字段，worker 会在运行时拿到 `KeyError`，而不是在编译时被拦下。

## 六、三个容易踩的坑

第一，混用静态边和动态路由。条件边和 `Command` 已经决定去哪了，再挂一条 `add_edge` 就会两条都走。判断方法很简单：一个节点要么静态出边，要么动态路由，二选一。

第二，把 `Command(update=...)` 当输入传给 `invoke`。文档写得很清楚：这个写法会从最新 checkpoint 继续跑，不是从 `START` 重启。想让新一轮从头发车，传普通 dict。`Command(resume=...)` 才是给 `invoke` 用的那个形式，这是第 09 篇的主题。

第三，以为扇出结果按顺序回来。并行实例的完成顺序由框架调度决定，合并顺序按 task path 排，不保证等于你的列表顺序。要顺序就在下游按 key 排序，别赌。

还有一个隐蔽的：条件边返回空列表就等于"这条分支到此为止"。列表为空时不会有任何节点被激活，图可能直接结束。我在过滤空任务时踩过，最后是靠在下游节点里判断"有没有结果"补上的。

## 七、怎么选

一句话版本：

- 路线固定 → `add_edge`；
- 看状态决定去哪 → `add_conditional_edges`；
- 刚算完的值直接决定去哪，还要顺手写状态 → `Command`；
- 条目数运行期才知道，每个条目单独跑 → `Send`；
- 从入口就分流 → 对 `START` 挂条件边。

文档还给了一条更好的判断线索：**这一步是在决定"接下来做什么"，还是在执行"已经决定的事"**。前者才需要分叉，后者老老实实当一个函数放在节点里，别为了图好看拆成一堆节点。

我自己的改法顺序是：先用静态边把流程跑通，跑不通的地方才换条件边；条件边写起来别扭了（要先写状态再读状态）才换 `Command`；条目数真的不固定了，最后才上 `Send`。一上来就 `Send` 加 `Command`，调试起来会很痛苦。

最后提醒一句递归上限：分叉容易写出环，默认的 super-step 上限是 10007（1.1.4 起），真跑飞了会抛 `GraphRecursionError`。看到这个错误，先检查有没有一条边在无条件地指回上游。
