# 第05篇：模型层怎么不写死｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 05 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

前四篇里，模型一直是个字符串，写在 `create_agent(model=...)` 里就完事。真实项目里它恰恰是最容易变的一层：涨价、限流、模型下线、换供应商，哪一样都不该让你改业务代码。

## 一、写死模型名要付四份代价

最直接的是换供应商：`ChatOpenAI` 换成 `ChatAnthropic`，import 和构造语句全得改，散在十几个文件里。第二份代价是限流时无路可退——主线模型 429，你只能干等。第三份是测试成本，跑一遍集成测试用的是最贵的模型。第四份是灰度，想按用户或按任务分流，代码里没有这个开关。

把模型层抽出来的目标就三条：**一处配置、按需覆盖、失败可退**。

举个具体例子：同一份代码要跑在开发、预发、生产三套环境，三套的模型配额还不一样。写死之后，你只能靠配置文件加代码两条路并行改，漏一处就是事故。

## 二、init_chat_model：一行换供应商

`init_chat_model` 是统一入口。模型名写成 `provider:model`，一段代码就能在 OpenAI、Anthropic、Gemini 之间挪。

```python
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-5", temperature=0)

bedrock = init_chat_model(
    "us.anthropic.claude-sonnet-4-6",
    model_provider="bedrock_converse",
    max_retries=10,
    timeout=120,
)
```

AWS 这种模型名里带点的，用 `model_provider` 单独给，别硬塞在冒号后面。`temperature`、`max_tokens`、`timeout`、`max_retries` 这些参数都是直接透传的。

比"一行切换"更值钱的是统一接口：不管底层是谁，返回都是 `AIMessage`，工具调用都在 `tool_calls`，用量都在 `usage_metadata`，流式都是 `AIMessageChunk`。业务层只跟这套接口打交道，换供应商时真正要动的，就是那一行字符串。

`max_retries` 的默认值因集成而异——`ChatOpenAI` 和 `ChatAnthropic` 默认 2 次，Gemini 默认 6 次，Ollama 不重试。这些重试只覆盖网络错误、429 和 5xx，401、404 这类客户端错误不会重试。长任务跑在不稳的网络上，调到 10–15 次是合理的。

## 三、能力别靠猜，读 profile

换模型最容易踩的坑，是假设它和上一个模型一样能干。`model.profile` 把这些能力摊开：

```python
model.profile["tool_calling"]        # 能不能调工具
model.profile["structured_output"]   # 支不支持原生结构化输出
model.profile["max_input_tokens"]    # 上下文窗口
```

这份数据来自 models.dev，LangChain 又补了一层字段。它不只是给你查的，框架自己在用：第 04 篇那个"传 Schema 自动选策略"，就是先查 `structured_output` 再决定走 Provider 还是 Tool；摘要中间件也靠 `max_input_tokens` 判断什么时候该压缩。

数据缺失或过期时可以直接覆盖，不用等发行版：

```python
model = init_chat_model(
    "my-model",
    model_provider="openai",
    profile={"tool_calling": True, "structured_output": True, "max_input_tokens": 100_000},
)
```

这份 profile 还能给前端用：模型选择器按 `tool_calling` 过滤，按 `max_input_tokens` 显示上下文大小，按支持模态决定要不要关掉图片上传。能力判断写在配置里，比散在代码各处的 `if provider == ...` 靠谱得多。

## 四、按任务选模型，不改代码

一个 Agent 里混用模型很常见：规划用强模型，执行用便宜模型，最后审稿再切回强模型。用 `wrap_model_call` 在请求上换掉模型，业务节点一行不用改。

```python
from langchain.agents.middleware import wrap_model_call

cheap = init_chat_model("openai:gpt-5-mini")
strong = init_chat_model("anthropic:claude-sonnet-4-6")

@wrap_model_call
def by_task(request, handler):
    state = request.state
    if state.get("stage") == "final_review" or len(state["messages"]) > 10:
        return handler(request.override(model=strong))
    return handler(request.override(model=cheap))
```

有个限制要记住：要做结构化输出时，别往中间件里传已经 `bind_tools` 过的模型实例，框架会报不支持。

省钱的账也要算清。一次强模型调用可能顶十次便宜模型，但换来的可能是少两轮工具调用、少一次返工。别为了省 token 把关键判断也交给小模型——它多绕两圈，账单和延迟一起涨。

另一种切法是按 run 覆盖，连中间件都不用写：`init_chat_model(temperature=0)` 不填模型名，模型本身就成了可配置项。

```python
configurable = init_chat_model(temperature=0)
configurable.invoke("你好", config={"configurable": {"model": "gpt-5-nano"}})
```

`configurable_fields` 还能把 `temperature`、`max_tokens` 一起变成运行时可调，`config_prefix` 用于一条链路里有多个模型时区分参数名。

## 五、失败分两种：重试和换人

429、5xx、超时、连接断开，这些是"等一会儿再来"。401、403、404、参数非法、上下文超限，这些是"再来一百次也一样"。区分标准不是猜，异常对象自己带 `is_retryable`。

重试交给 `ModelRetryMiddleware`，默认重试 2 次，退避是指数的，抖动 ±25%。

```python
from langchain.agents.middleware import ModelFallbackMiddleware, ModelRetryMiddleware

agent = create_agent(
    model="openai:gpt-5",
    tools=[...],
    middleware=[
        ModelFallbackMiddleware("openai:gpt-5-mini", "anthropic:claude-sonnet-4-6"),
        ModelRetryMiddleware(max_retries=3, backoff_factor=2.0, initial_delay=1.0, max_delay=60),
    ],
)
```

中间件列表的顺序就是包裹顺序。`Fallback` 写在前面，它就是外层：主模型把重试耗尽之后，才轮到下一个模型上场；换上去之后照样走重试。反过来写，就变成"每个模型只试一次"，白白浪费了重试预算。

`on_failure` 决定重试耗尽后的行为：默认 `continue`，返回一条带错误信息的 `AIMessage` 让 Agent 自己往下走；改成 `error` 就直接抛出，让上层兜。

切备模型本身要挑能力对齐的：支持工具调用、支持同样的模态、结构化输出不会从 Provider 掉到 Tool。否则切过去不是降级，是换了个干不了这活的模型，错误从 429 变成答非所问。

## 六、限流和预算，得单独管

限流不是重试能解决的。`rate_limiter` 在客户端先把请求节流，别等服务端打回来。

```python
from langchain.rate_limiters import InMemoryRateLimiter

limiter = InMemoryRateLimiter(
    requests_per_second=0.1,     # 10 秒放一个请求
    check_every_n_seconds=0.1,   # 每 100ms 检查一次
    max_bucket_size=10,          # 允许的突发量
)
model = init_chat_model("openai:gpt-5", rate_limiter=limiter)
```

它只限请求数，不限请求大小——长上下文照样能把账单顶上去。预算要靠 `usage_metadata` 统计：

```python
from langchain_core.callbacks import get_usage_metadata_callback

with get_usage_metadata_callback() as cb:
    agent.invoke({"messages": [{"role": "user", "content": "..."}]})
print(cb.usage_metadata)
```

按模型名分组拿输入、输出和总 token，多模型混跑时这条数据比日志有用。

生产上更常见的是按用户做配额：把用量落到库里按天聚合，超了就降级到便宜模型，或者干脆给用户一个明确的提示。限流防的是被厂商打回来，配额防的是账单失控，两件事不能互相替代。

## 七、还有一层：拒绝也是正常响应

厂商的安全拒绝不是异常，是一次成功的调用，返回一个 `refusal` 内容块。不加处理，Agent 会把"我拒绝回答"当成最终答案交出去。

`ModelRefusalMiddleware` 把它变成 `ModelRefusalError`，这样才能被 `Fallback` 接住、换下一个模型重试。它要放在 `Fallback` 后面（也就是内层），顺序反了就拦不到。

这个中间件需要 `langchain>=1.4.9`。不用它也行，自己在 `wrap_model_call` 里检查 `content_blocks` 里的 `refusal`，做记录或者 `interrupt()` 找人。

流式场景还有个小坑：拒绝之前的文本可能已经吐给前端了，中间件抛错也收不回来。所以对敏感场景，要么先判后流，要么在前端留一个可撤回的展示位。

## 八、小结

模型层其实就三件事：**选**（`init_chat_model` 加 profile）、**切**（`wrap_model_call` 或 configurable）、**兜**（重试、切备、限流）。

顺序也有讲究：先把选和切做对，再谈兜底。选错了模型，重试只是更快地烧钱。

最后提醒一句：换模型不等于换了个插头。提示词长度、工具描述的颗粒度、结构化输出的可靠性，都跟着模型变。切完之后一定要拿回归集跑一遍，别只看能不能返回。
