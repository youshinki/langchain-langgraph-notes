# 第02篇：消息列表多了什么｜LangGraph系列

欢迎来到《把 Agent 画成图》系列，这是第 02 篇。全系列 18 篇，从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

上一篇把循环拆成四步。这一篇换个角度看同一件事：不看步骤，看数据。

一次 `invoke` 结束，agent 的状态里只有一样东西——消息列表。它从 1 条变成 4 条，每一条都能解释循环走到了哪一步。

## 一、列表从 1 条变成 4 条

先给结果。用第 01 篇那个离线脚本跑一遍，输出是这样的。

```text
 0 user       LangGraph 1.2 改了什么？
 1 assistant  我先查一下资料。 tool_calls=1
 2 tool       {"query": "...", "hits": [...]} tool_call_id=call_001
 3 assistant  整理完了：1.2 的主线是节点级控制。
```

四条消息，三种角色。第一条是问题，第二条是模型决定动手，第三条是工具跑完的结果，第四条是模型收尾。

循环的终止条件就藏在第四条里：`tool_calls` 为空。

注意第二条的 `content` 不是空的——模型可以先说一句"我查一下"再动手。文本和工具调用能同时存在，不是二选一。

如果是并行调用，第二条会带三个 `tool_calls`，第三步就变成三条 Tool 消息，一次循环多出四条。所以"列表多了几条"不固定，取决于模型这一轮决定同时动几个工具。

要注意的是，这不是"聊天记录"。聊天记录可以只留文本，状态不行。第二条里那个 `tool_calls` 数组、第三条里那个 `tool_call_id`，都是模型和工具之间的协议字段，少一个，下一轮就谈不下去。

多轮对话里，这个列表只会越来越长。每轮至少两条，带工具的四条起，十轮之后就是几十条。token 是这么涨上去的，第 05 篇讲压缩，根子在这里。

## 二、四类消息，各自管一件事

**System 消息**定角色。它通常不在 `state` 里——`create_agent(system_prompt=...)` 是在每次调模型之前把这段指令拼上去，属于 middleware 的活。所以翻状态找不到它，也解释了为什么动态提示词必须走中间件，而不是靠往列表里塞一条。

顺带说清一个常见误会：`system_prompt` 不等于"往 messages 里插一条 SystemMessage"。前者每次调用时拼，后者会进状态、占 token、被检查点保存。要改前者用 middleware，要动后者才改列表。

**Human 消息**是输入。除了文本，还能带图片、音频、文件；多条 `HumanMessage` 用 `name` 字段区分是谁说的，比如多用户场景。

**AI 消息**是模型产出。除了 `content`，它还挂着 `tool_calls`、`usage_metadata`、`response_metadata`、`id`。`usage_metadata` 里有输入输出 token 数，算成本就靠它；`response_metadata` 存 provider 的原始返回，排查怪问题时用得上。

`id` 看着不起眼，但它决定这条消息在列表里是"新增"还是"更新"，流式合并和断点重放全靠它。

从 1.0 起，`content` 不再只是字符串。标准 content blocks 把文本、推理、拒答、工具调用、图片统一成了带 `type` 的字典，换 provider 不用改解析逻辑。这是一次性收益，后面几乎每篇都会用到。

**Tool 消息**是工具结果，两个字段必填：`tool_call_id` 和 `name`。还有一个字段值得单独说——`artifact`。它不会发给模型，只留在程序里。检索场景可以这样用：`content` 放给模型读的摘要，`artifact` 放原文、文档 id、页码，前端要引用时直接取。用好了，token 能省一大截。

另外 `content` 必须是字符串。工具返回 dict 就先自己 `json.dumps`，别指望框架替你排版——它转出来的格式未必是你想要的。

## 三、tool_call_id 是唯一对账凭证

模型一次可以发多个 `tool_calls`，并行调三个工具很常见。规则只有一条：**每个 call 必须有且只有一条 `ToolMessage`，id 对上。**

少一条，provider 直接返回 400，报错大意是"tool_call_id 没有对应的 tool 消息"。id 对不上，模型会以为自己没拿到结果，再调一次。

还有个隐坑：模型偶尔返回 `invalid_tool_call`，参数不是合法 JSON。这时别硬执行，回一条说明参数解析失败的 ToolMessage，让它重发，比抛异常强。

手拼消息时最容易错两处。一是自己编号，比如 `call_1`、`call_2`，而忘了用模型返回的 id；二是漏了 `name`——在 v1 里它是必填字段，不是可选装饰。

```python
ToolMessage(
    content="Sunny, 72F",
    tool_call_id="call_123",   # 必须等于 AIMessage 里的那个 id
    name="get_weather",
)
```

多条并行时顺序不重要，id 重要。工具跑得快慢不一，谁先回来谁先入列，模型照样能对上。

调试 id 不匹配有个笨办法，但有效：打印最后一条 AIMessage 的 `tool_calls`，再打印它后面所有 Tool 消息的 `tool_call_id`，两边做差集。缺哪个，问题就出在哪个工具上。

并行还有个副作用：三个工具的结果会集中堆在列表里，一次三篇网页全文就能把上下文吃掉一半。并行不是越多越好，第 07 篇讲 `Send` 时会再算这笔账。

## 四、工具报错，别让异常飞出去

1.0 把工具错误处理挪到了 middleware 的 `wrap_tool_call`。不写这层，工具抛异常就一路抛到图外，循环当场断掉。

更常见的做法是接住，回一条带错误信息的 `ToolMessage`，让模型自己决定重试还是换路：

```python
@wrap_tool_call
def catch_tool_error(request, handler):
    try:
        return handler(request)
    except TimeoutError as e:
        return ToolMessage(
            content=f"tool_timeout: {e}", tool_call_id=request.tool_call["id"],
            name=request.tool_call["name"], status="error",
        )
```

边界在于错误信息写得够不够具体。只写 `failed`，模型会原样重试同一个调用；写清是参数错、权限错还是超时，它才会改参数或换工具。

还有一种情况该让它抛：工具遇到"不该继续"的硬错误——鉴权失效、余额不足、目标不存在——抛出去让外层中止，比让模型瞎猜更省事。可恢复的错才回消息。

## 五、add_messages：两条规则决定列表怎么长

`State` 里那行声明是关键：

```python
from typing import Annotated
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]
```

规则一：**默认追加**。节点返回 `{"messages": [...]}`，新消息接在尾部。

规则二：**同 id 覆盖**。同一个 `id` 再次出现时替换旧的，不新增。流式 chunk 合并成完整消息、断点重放，靠的都是这条。

删除走另一条路：`RemoveMessage(id=...)`。摘要压缩的典型写法就是先删旧消息、再插一条摘要：

```python
rm = RemoveMessage(id=m.id)
new_state = {"messages": [rm, HumanMessage("前文摘要：...", id="summary_1")]}
```

流式场景更直观：`AIMessageChunk` 一块一块来，最后用 `+` 拼成完整消息，id 相同，所以列表里始终只有一条。

这两条规则合起来，意味着**手工造消息必须给 id**。不给，重放时同一段内容会重复进列表，token 翻倍，还查不出原因——这类问题最后都落到"消息 id 没管好"。

还有一个直接后果：检查点保存的就是这个列表。消息设计得好不好，决定了断点续跑贵不贵——第 08 篇会看到，长列表是检查点体积的主要来源。

## 六、这一圈记住三件事

第一，状态就是消息列表，没有别的隐藏字段。想知道 agent 现在处于哪一步，看最后一条消息的角色就够了。

第二，消息是协议，不是日志。`tool_calls` 和 `tool_call_id` 必须成对，`ToolMessage` 的 `name` 不能省，`content` 必须是字符串。

第三，调试先打印。整段 `pretty_print()`，比读十行日志快。
