# 第10篇：流式到底流什么｜LangGraph系列

欢迎来到《把 Agent 画成图：18 篇吃透 LangChain 与 LangGraph》，这是第 10 篇。从 LangChain 1.x 的 `create_agent` 讲到 LangGraph 运行时，再到工程化落地。

第 09 篇讲完人审，这一篇讲前后端之间最容易被糊过去的一层：流式。很多人以为"流式"就是把模型吐字接出来，可图跑起来之后，你还会想看到节点更新、工具进度、子图嵌套、检查点写入。LangGraph 把这些拆成了好几个通道，先认清通道，再谈接前端。

## 一、别把两层混成一层

LangGraph 的流式其实有上下两层。

底层是 `stream()` / `astream()` 加 `stream_mode`，直接吐运行时事件：`values`、`updates`、`messages`、`custom`、`checkpoints`、`tasks`、`debug`。你要什么就先声明什么，像打开几个水龙头。

上层是 1.2 起推出的 event streaming：`stream_events(..., version="v3")`，把底层事件归一化后交给一组 transformer，产出**有类型的投影**，比如 `stream.messages`、`stream.values`、`stream.subgraphs`、`stream.output`。

官方现在的口径很明确：**新应用优先用事件流**，需要低层原始事件时再用 `stream_mode`。原因不难理解，下面会看到。

## 二、七个 mode 各管什么

先用一张表把分工记住。

| mode | 给你什么 | 前提 |
|---|---|---|
| `values` | 每一步之后的完整状态 | 无 |
| `updates` | 每一步之后的状态增量，带节点名 | 无 |
| `messages` | 大模型吐的 token 与元数据 | 无 |
| `custom` | 节点里自己写出去的自定义数据 | 无 |
| `checkpoints` | 检查点事件，格式同 `get_state()` | 需要 checkpointer |
| `tasks` | 任务的开始/结束、结果与异常 | 需要 checkpointer |
| `debug` | 上面两类再加上额外元信息 | 需要 checkpointer |

两个容易记错的点：`updates` 在同一个 step 里的多次更新是**分开吐**的，不会合并成一条；`messages` 即使模型用的是 `invoke` 而不是 `stream`，token 事件照样有，这层是运行时自己切的。还有 `checkpoints` 和 `tasks`，它们依赖 checkpointer，没配就什么都没有——排查"流是空的"时先看这一条，比看代码快。

写进度条就用 `custom`：节点里 `get_stream_writer()` 拿 writer，把字典扔出去，前端拿到就能渲染。这个通道不关心你底层调的是哪家模型，所以连不走 LangChain 接口的模型也能接进来。

```python
from langgraph.config import get_stream_writer

def retrieve(state):
    writer = get_stream_writer()
    writer({"status": "检索中", "done": 3, "total": 10})
    return {"docs": load_docs(state["query"])}
```

## 三、v1 的返回形状，才是真麻烦

问题出在格式。默认的 v1 会按你的选项换形状：

```python
# 单 mode：直接给数据
for chunk in graph.stream(inputs, stream_mode="updates"):
    print(chunk)          # {"node": {...}}

# 多 mode：(mode, data) 二元组
for mode, chunk in graph.stream(inputs, stream_mode=["updates", "custom"]):
    ...

# 开子图：(namespace, data) 二元组
# 多 mode + 子图：(namespace, mode, data) 三元组
```

于是前端代码里全是分支判断：这条是二元组还是三元组、第一个元素是 mode 还是 namespace。加一个 mode，就可能得改一遍解析。这类活儿不难，但很碎，而且最容易在"本地只有单 mode"时看不出来。

## 四、v2 把形状统一成三段

LangGraph 1.1 起支持 `version="v2"`，所有 chunk 都是同一个 `StreamPart`，三个字段：`type`、`ns`、`data`。

```python
for part in graph.stream(inputs, stream_mode=["values", "updates", "messages"],
                         version="v2"):
    if part["type"] == "values":
        print(part["data"]["topic"])          # 完整状态
    elif part["type"] == "updates":
        for node, delta in part["data"].items():
            print(node, delta)                # 增量
    elif part["type"] == "messages":
        msg, meta = part["data"]              # token + 元数据
        print(msg.content, end="")
```

好处有两层。工程上，解析逻辑只剩一个 `type` 分支，加 mode 不改结构；类型上，`StreamPart` 是按 `type` 判别的联合类型，编辑器里 `if part["type"] == "values"` 之后，`data` 会自动收窄成对应结构。

`ns` 是命名空间元组，根图是空元组 `()`，进了子图才会有值。v2 下它永远在同一个位置，不用再猜。

顺带一个容易忽略的升级：`invoke(..., version="v2")` 返回的是 `GraphOutput`，用 `.value` 拿状态、`.interrupts` 拿中断，不再把中断塞在 `__interrupt__` 键里。字典式访问还能用，但已标记废弃。

## 五、messages 的三个过滤器

`messages` 是前端最关心的通道，但一个图里往往不止一处调模型。元数据里带了足够的信息，可以只挑你要的那一路：

```python
for part in graph.stream(inputs, stream_mode="messages", version="v2"):
    if part["type"] != "messages":
        continue
    msg, meta = part["data"]
    if meta["langgraph_node"] == "write_answer" and msg.content:
        print(msg.content, end="")
```

三种过滤方式各有用途：`langgraph_node` 按节点挑；给模型加 `tags=["joke"]`，再按 `meta["tags"]` 挑，适合一个节点里调两次模型的场景；反过来，给模型配 `nostream` 标签，它的 token 就完全不进流——比如结构化输出那次调用，你只要结果不要过程。

## 六、子图：为什么 token 突然没了

这是踩坑率最高的一条。`create_agent` 返回的是一个**编译好的图**，你把它当节点塞进父图，它就成了子图。

这时父图 `stream_mode="messages"` 收不到里面那层模型的 token，必须加 `subgraphs=True`。而直接调 `agent.stream(...)` 是能收到的，所以问题常常出现在"包了一层之后"。

开了子图，事件会带上命名空间，形如 `("agent:<task_id>",)`，v2 下统一放在 `ns` 里。前端按 `ns` 判断这条 token 来自哪个子图、哪个节点，就能做"研究员在写、审查员在改"这种分栏展示。

有一点要留意：`subgraphs=True` 是"打开"而不是"过滤"，父图自己的事件也在里面流，所以前端必须靠 `ns` 判空来区分根图和子图，不能默认收到的一定是子图。层级再深一层，`ns` 就再长一段，按 `:` 切出名字即可。

## 七、v3：一次 run，多个投影

再往上就是事件流。`graph.stream_events(input, version="v3")` 返回一个 run 对象，上面挂着一排投影：

```python
stream = graph.stream_events({"messages": [{"role": "user", "content": "你好"}]}, version="v3")
for message in stream.messages:
    for token in message.text:
        print(token, end="", flush=True)
final_state = stream.output
```

投影清单大致如下：

- `stream.messages`：消息与 token，`message.text` 可迭代，`message.reasoning` 是思考增量，`message.tool_calls` 是工具调用片段
- `stream.values` / `stream.output`：状态快照与最终结果
- `stream.subgraphs`：子图，直接给 `graph_name` 和 `path`，不用自己拆命名空间
- `stream.interrupts` / `stream.interrupted`：中断载荷与是否暂停
- `stream.extensions`：自己注册的 transformer 产出的投影

关键在于**并发**：多个消费者可以同时读不同投影，读 `messages` 不会把 `values` 需要的事件消耗掉。同步代码里想按到达顺序混着读，用 `stream.interleave("values", "messages", "subgraphs")`；异步里就 `asyncio.gather` 起几个协程各读各的。

要原始协议事件，直接迭代 run 对象，每条都是 `ProtocolEvent`：`seq` 在单次 run 内严格递增，用来排序；`method` 是通道名；`params.namespace` 是从根图到发出者的路径，根是 `[]`；`params.timestamp` 是墙钟毫秒，官方明确说会漂、别拿它排序。

通道大致这么分工：`values` / `updates` 管状态，`messages` 管模型输出，`tools` 管工具开始、输出、结束、报错，`lifecycle` 管 run、子图、子 agent 的状态变化，`checkpoints` 管检查点，`input` 管人审请求。`messages` 通道是按内容块组织的：块开始、若干 delta、块结束，delta 分 `text-delta`、`reasoning-delta`、`data-delta`、`tool-call-delta`；遇到不认识的类型忽略就好，别让一条新 delta 把整个流打断。

## 八、一句话收尾

选型可以很干脆：**接前端、要打字机效果和多视图，用 `stream_events(version="v3")` 的投影；要排查底层事件、或者只取一个通道，用 `stream_mode` 加 `version="v2"`。**

还有一个环境坑得提前说：Python 3.11 以下跑异步，必须把 `config` 显式传给 `ainvoke()`，`get_stream_writer()` 也不可用，得在节点签名里加 `writer` 参数由框架注入。这不是配置问题，是 asyncio 上下文传播的历史限制，升到 3.11+ 就没了。

最后补一句实践建议：流式的价值不在"看起来快"，而在于让用户在执行过程中就能判断对不对。所以别只把 token 接出来，把节点进度、工具调用、子图切换也一起给出去——用户看见图在走，才敢把长任务交给你。
